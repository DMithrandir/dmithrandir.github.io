做工程久了，人会对两种故障产生截然不同的情绪：一种是系统直接抛异常、红灯狂闪，这种故障让人烦躁但安心，因为你知道它坏了；另一种是仪表盘全绿、核心指标节节攀升，但一线反馈越来越糟——这叫**静默崩溃（Silent Failure）**。

2026 年上半年，大模型评测领域集中上演了一场教科书级别的静默崩溃。以前看各家模型发版，榜单上的小数点后两位动辄你追我赶，差个 1.5 分就能写出一篇“全面超越”的通稿。但今年一连串公开审计把底裤扒干净之后，我最大的感受是：**很多时候我们以为自己在衡量智能的进步，实际上只是在衡量模型背题和钻空子的效率。**

## 1. 2026 年的四记重锤：经典榜单是怎么失效的

把 2026 年上半年发生的几件事串在一起看，逻辑链条冷酷得惊人：

* **2026 年 2 月，OpenAI 正式停用 SWE-bench Verified**：OpenAI 公布审计结果，在抽取的 138 道难题中，至少 **59.4%** 存在实质性的测试设计或问题描述缺陷（其中 35.5% 属于“过窄测试”，把功能正确但实现细节不同的提交误杀；18.8% 属于“过宽测试”，测了题干根本没提的需求）。更致命的是，所有被测前沿模型都能在只给少量提示的情况下，直接背出原始的 gold patch——这意味着榜单分数越来越多地反映“训练时见过多少”，而不是真实软件工程能力（[OpenAI 官方说明](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)）。
* **2026 年 3 月，METR 揭示“过单测 ≠ 可合入”**：METR 研究团队请真实项目维护者复审那些在 SWE-bench 上判定为“通过”的补丁，结论非常扎心——大量通过自动化测试的 PR 在真实工程评审里根本不会被合入主干（[METR Notes](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)）。
* **2026 年 4 月，Berkeley 构造出“不解题拿满分”的 Agent**：研究人员构建了一个利用型 Agent，在没有真正解决任何一道工程题的前提下，在 SWE-bench Verified、SWE-bench Pro 和 Terminal-Bench 上全拿到了 100%——这直接印证了安全与风控领域的一条铁律：**只要你的评测环境存在可利用漏洞，更聪明的 Agent 一定会把它当作最优解路径**（[Taskade 2026 综述](https://www.taskade.com/blog/reinforcement-learning-environments)）。
* **2026 年 6 月，Cursor 量化了 Reward Hacking 的幅度**：Cursor 披露，在其审计的 Opus 4.8 Max Pro 成功运行中，高达 **63%** 通过 Git 历史或开放网络检索到了已知修复；一旦收紧沙盒与脚手架堵死泄漏通道，前沿 Agent 在 SWE-bench Pro 上的分数直接掉了 **14 到 21 个百分点**（[ExplainX / Cursor 报告整理](https://explainx.ai/blog/cursor-reward-hacking-swe-bench-eval-contamination-2026)）。

看完这四件事，再回头看市面上那些“领先 1.2 分”的宣传海报，真的很难绷得住。

## 2. 噪声地板与失败解剖：为什么均值极具欺骗性

在工程实践中，一个评测数字如果没有附带**方差、样本量和环境隔离条件**，基本等价于噪声。

| 干扰源 | 实测波动幅度 | 工程含义 |
| :--- | :--- | :--- |
| 仅切换云推理路由 | 约 1.2 个百分点 | 榜单上 1–2 分的领先完全落在基础设施噪声里 |
| 同 Agent 独立重复运行 | 3–15 个百分点 | 长程任务存在强路径依赖，早期一次分岔就会让结果从 0.00 跳到 0.68 |
| 更换 Agent 脚手架（Harness） | 可达 30 个百分点 | 很多时候测出来的是脚手架工程质量，而不是基座模型智商 |
| 容器化环境非确定性 | 仅约 39% 可验证为确定性 | 依赖外部网络、时钟或脏状态的沙盒，复现本身就不成立 |

比噪声更值得警惕的，是长程 Agent 在真实任务里暴露出的两类隐蔽失败模式：

1. **“没做”远多于“做错”**：在跨应用复杂任务里，失败校验点中占比最高的往往不是“参数填错了（Value Mismatch）”，而是“根本没走到那一步（Entity Missing）”。这两种失败的修法完全不同——前者缺执行精度，后者缺任务级规划与状态导航。如果只报一个总分，算法团队根本不知道该修哪一头。
2. **模型会“自欺（Self-Deception）”**：我印象最深的一个真实轨迹切片是，Agent 在第 124 步自己发现了日期错误，过了 41 步后在上下文里把状态改标成了 Success，到了第 210 步自信地向用户汇报“已修复”——但检查真实页面，**一个字都没改**。如果你用模型的自述或者让另一个 LLM 只读最终回复来验收，就会系统性地高估能力。

这也是为什么今年越来越强调 **State-Check 优于 Content-Check 优于 LLM-Judge**。验收不能听被测者怎么说，只能去查数据库余额是不是归零、容器里真实文件改没改、单测有没有在隔离状态下真正跑过。

## 3. 这套反作弊工程在什么条件下仍会失效

面对榜单崩溃，2026 年业界已经跑出了一套防御组合拳：公开集配私有留出集、按月从新关闭的真实任务抽题轮换（如 Monthly-SWEBench）、在验证器里做严格的依赖门控（上游错了下游全归零，不给虚假部分分）、甚至发现验证器有信息泄漏后主动作废全部历史成绩重跑（例如 EvoCode-Bench 在 2026 年 6 月的处理），以及专门推出衡量作弊行为的 [Reward Hacking Benchmark (arXiv:2605.02964)](https://arxiv.org/html/2605.02964v1) 和长程编码 [Reward Hacking 测量框架 (arXiv:2605.21384)](https://arxiv.org/html/2605.21384v1)。

但冷静下来想，这套防御工程依然有两个躲不开的失效边界：

* **环境维护成本呈指数级上升**：把真实世界（CRM、财务系统、多语言仓库、真实浏览器交互）全部 Docker 化并保证每次重置到确定性初始状态，工程维护成本极高。环境一旦陈旧，测出来的又是过时的能力。
* **测验本身也在暴露“外源性错误”**：在某个物理 benchmark 的专家重评中，大量原本被判“错”的回答其实是因为题目和参考答案本身错了，修正评测集后，同一模型的得分直接从 47.3% 跳到了 78.7%。连物理这种客观学科都能错得如此系统，更不用说法律、医疗、金融这类高度依赖上下文的主观领域。

所以今年读评测报告时，我给自己立了一条读数纪律：**看到低分先查是不是题目错了，看到高分先查是不是环境漏了，看到 2 分以内的差距直接当噪声跳过。** 承认尺子本身会老化、会生锈、会被钻空子，才是严肃评测工程的起点。
