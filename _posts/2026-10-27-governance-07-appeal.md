## 〇、先纠正一个前提误区

**❌ 误区**：申诉是"客服功能"——用户不服气就让他申诉，审掉即可，属于成本中心。
**实情**：申诉在全链路里有**三个身份**，而第三个几乎无人使用。

| 身份 | 内容 | 归属 | 常见误区 |
|---|---|---|---|
| **① 用户权益通道**| 纠正错误处置，恢复内容 / 账号 / 收入 | 产品 + 运营 | 被认为"做到这就够了" |
| **② 质量信号源**| 暴露误伤、规则缺陷、审核认知偏差 | M3 + M1 + M4 | 被当工单处理掉 |
| **③ 唯一的证伪机制**| **能推翻"第一判"**，是误伤率唯一的直接测量口径 | **全链路**| 几乎无人意识到 |

### 0.1 为什么第三个身份最关键

前面几个环节都在**生产判断**，只有申诉在生产**关于判断的判断**：

| 环节 | 判什么 | 能否知道自己判错了 |
|---|---|---|
| 机审（M2） | 判定内容 | ❌ 不能 |
| 人审（M3） | 判定内容，并提供"真值" | ❌ 不能（不知道自己判错了） |
| **申诉（M5）**| **判定"判定"本身对不对**|  **能**|

**推论（本篇最重要的一条）**：

> **一个没有申诉统计的治理体系，无法知道自己的误伤率。**
> 它只能看漏放（VVR、举报率、低质 VV 占比），而**误伤是完全不可见的**。

这也解释了 M4 为什么只能拿"**申诉成功率**"当误伤率的**代理**指标（M4 §2.2）——因为在申诉之外，没有任何环节能稳定产出"判决被推翻"的数据。

### 0.2 申诉在链路中的位置

```
M0 发现 → M1 定义 → M2 实现 → M3 召回 → 审核 → 判罚处置
                                                    │
                                          ┌─────────┴─────────┐
                                          ↓                   ↓
                                    M9 举报（消费者）    M5 申诉（被处置方）
                                    "该审的没审"         "不该罚的罚了"
                                          │                   │
                                          └─────────┬─────────┘
                                                    ↓
                                        M0 候选问题 / M1 规则迭代 / M2 训练样本
```

⚠️ **一个结构性观察**：**举报与申诉是同一个攻击面的两侧**——
- **举报**：攻击者**送内容进审核**（消耗审核资源、打击竞品）
- **申诉**：攻击者**要求撤销处罚**（消耗复核资源、试探规则边界）

→ 两者的防滥用机制应统一设计（M9 §五、M6）。

## 一、申诉的特殊性：唯一由"被处置方"发起的环节

| 特性 | 后果 |
|---|---|
| **举证责任倒置**| 平台已作处置（推定违规），申诉人需举证自己被冤枉 |
| **只有一部分人会申诉**| 能力不对等：会写、有动力、知道入口的人才会申诉 → **系统性选择偏差**|
| **动机混杂**| 真误伤 / 不服气 / 想恢复收入 / 试探规则边界，全部混在一起 |
| **成本落在"少数人"身上**| 误伤成本由创作者 / 商家承担，而他们是最敏感的一群（M3 §六.3） |
| **有时效硬约束**| 内容/收入已被停掉，用户诉求是"立即" |

### 1.1 由此推出的第一条纪律

> **申诉率低 ≠ 误伤少。**
> 可能只是入口隐蔽、用户不知道能申诉、或申诉成本太高。

**所以申诉率的绝对值没有意义**，只有在配合申诉成功率、并经过抽样审计之后才有意义。

## 二、模块结构：申诉的七个组件

**这一节是本篇的骨架**——申诉作为一个业务模块，由这七块构成：

| # | 组件 | 核心问题 | 主要产出 |
|---|---|---|---|
| **1**| **入口与触达**| 用户从哪里、以什么形式发起？ | 申诉工单 |
| **2**| **受理与分类**| 这条申诉是什么性质？该走哪条流？ | 分流结果 |
| **3**| **复审与判定**| 谁有权改判？依据什么？ | 改判 / 维持 |
| **4**| **改判执行**| 改判后要恢复什么？ | 恢复动作 |
| **5**| **结果透传**| 怎么让用户理解并信任结论？ | 通知与理由 |
| **6**| **数据与归类**| 申诉数据怎么变成可用的信号？ | 三类归因 |
| **7**| **回流闭环**| 信号回给谁？改什么？ | 规则/审核/模型迭代 |

### 2.1 组件一：入口与触达

| 维度 | 设计要点 |
|---|---|
| **入口位置**| 处置通知里必须带入口（用户需先知道自己被处置了） |
| **多入口并存**| 站内申诉 / 客服工单 / 外部渠道（监管转办、公开投诉）→ **同一套判定口径，不同入口**|
| **理由结构化**| 让用户选"我认为哪一点判错了"（判定错误 / 规则不适用 / 证据缺失），而非纯自由文本 → **可归类、可统计**|
| **举证引导**| 给明确的举证清单；举证质量直接决定复审可行性 |
| **时效承诺可见**| 承诺 SLA 必须兑现，否则削弱下一次申诉意愿 |

⚠️ **入口可达性是一个治理诚信问题**：入口越隐蔽 → 申诉率越低 → **误伤越不可见**（§1.1）。把入口做浅，等于主动放弃自己的误伤测量能力。

### 2.2 组件二：受理与分类（模块的核心分流器）

申诉必须在受理阶段就分流，否则后续所有指标都会混在一起。

| 分流维度 | 分类 | 走向 |
|---|---|---|
| **按误判责任**| 判罚错误 / 规则缺陷 / 信号污染（§四） | 三条不同的处置与回流路径 |
| **按影响面**| 高影响 / 常规 / 低影响 | 三条不同的 SLA（§三.3） |
| **按处置对象**| 内容级 / 账号级 / 权限级 / 资金级 | 不同的恢复动作（§2.4） |
| **按可申诉性**| 可申诉 / 有限申诉 / 不可申诉（§五.2） | 决定是否受理 |

### 2.3 组件三：复审与判定

**这一块最容易设计错，因为它牵涉权限正义**。

| 设计项 | 说明 |
|---|---|
| **复查主体**| 原审核团队 / 独立复审团队 / 专职申诉队列 |
| **复查层级**| 单审 / 双审 / 升级审（高风险案件） |
| **判定依据**| 标准原文 + **判例**（同类既往申诉结论）+ 举证材料 |
| **改判权限**| 谁能改判？能否改判规则本身？ |

⚠️ **一个必须避免的结构性问题**（详见 §五.1）：**不能用"原审核团队"复审自己团队的判罚**。

### 2.4 组件四：改判执行

**改判不是一个动作，而是一组动作**——漏掉任何一个都会造成"判改了但用户没感知"：

| 层级 | 恢复动作 | 常见遗漏 |
|---|---|---|
| **内容级**| 恢复内容 / 重新进入推荐池 | 恢复了但没重新推，用户仍无流量 |
| **账号级**| 解除限制、恢复权限、清除违规记录 | 处罚撤销了但**信用分/历史记录未回滚**，影响后续权益 |
| **资金级**| 恢复收益、退还罚金 | 收益恢复有账期，需明确时效 |
| **后续影响**| 撤销对推荐模型负向信号的影响（M3 §6.2） | **几乎无人处理**：负向信号已进入训练数据 |

⚠️ **最后一行是最隐蔽的**：审核结果作为推荐模型的负向信号（M3 §6.2），**改判后这批样本已经污染了训练数据**。→ 改判执行应包含"**从训练样本中剔除**"的动作。

### 2.5 组件五：结果透传

| 要点 | 为什么 |
|---|---|
| **必须给理由**| 只说"维持原判"会激化不信任；应引用**规则条款**或判例 |
| **区分"判错"与"规则如此"**| 类型 ② 的申诉应明确告知"我们按规则判罚是准确的，但这个规则我们会评估"——**这是把规则缺陷转化为用户可理解的信息**|
| **不透传过细的判定依据**| 防止被用来试探规则边界（M9 §五 的试探型滥用） |
| **承诺时效可见**| 与 §三.3 的分层 SLA 一致 |

### 2.6 组件六：数据与归类

申诉数据的价值不在"处理完了"，而在**归到哪一类**（§四）。

### 2.7 组件七：回流闭环

| 归因 | 回流给谁 | 改什么 |
|---|---|---|
| **判罚错误**| M3 | 审核培训、认知对齐、双审一致率 |
| **规则缺陷**| **M1**| 规则表述、边界定义、处置梯度 |
| **信号污染**| M9/M6 | 防滥用机制 |
| **（附带）判例**| 全链路 | 正负判例库（"为什么不违规"与"为什么违规"同等重要） |

⚠️ **建议沉淀两类判例**：
- **"为什么违规"的判例**→ 防漏放
- **"为什么不违规"的判例**→ 防误伤（**多数团队只做前者**）

**技术侧印证**：KuaiMod 对"模型判对、但用户仍感不适"的样本，会让大模型**列举可能引起不适的方面并解释为何不违规**，用于教模型区分**个体敏感 vs 社会共识**。这与申诉侧沉淀负向判例是同一种思路。

## 三、指标口径（本模块最硬的一节）

### 3.1 漏斗与口径定义

**申诉模块的指标必须严格区分"案件级"与"处置级"**——一个处罚可能产生多次申诉，一个用户可能对同一处罚在多入口申诉。

| 层 | 指标 | 分子 / 分母 | 关键注意 |
|---|---|---|---|
| **规模**| **申诉率**| 申诉数 / **处置数**| 分母是**处置数**（不是内容数、不是活跃用户数）；按处置类型分层看才有意义 |
| | **申诉覆盖率**| 有申诉的处置数 / 总处置数 | 与申诉率不同：前者看"有多少处置被挑战过" |
| **质量**| **申诉成功率**| 申诉成功 / 申诉总数 | ⚠️ **必须以"案件"为单位去重**，否则多入口重复申诉会稀释 |
| | **改判率**| 改判数 / 复审完成数 | 与申诉成功率接近，但含"部分改判" |
| | **维持率**| 维持原判 / 复审完成数 | ≠ 申诉失败率；需区分"维持"与"不予受理" |
| **效率**| **申诉处理时效**| P50 / P90 / P99（受理 → 结论） | **必须分影响面分层报**|
| | **申诉转化成本**| 单件复审成本（人力 + 算力） | 决定申诉体系的人力天花板（同 M3 §2.5） |
| **信号**| **源头修正率**| 因申诉而修订的规则数 / 申诉总量 | **本模块最有价值但最少被统计的指标**|
| | **误伤率（上下界）**| 见 §3.3 | 需抽样审计，不能只看申诉池 |

### 3.2 ⚠️ 一处必须区分的分母：三种"申诉成功率"

**同一个名字，三个完全不同的分母——混用会导致结论完全相反**：

| 分母 | 指标含义 | 回答什么问题 |
|---|---|---|
| **申诉总数**| 申诉成功 / 总申诉 | 用户诉求的满足程度 |
| **复审完成数**| 改判数 / 已复审数 | 复审环节的判定倾向 |
| **处置总数**| 申诉成功 / 总处置 | **对处置准确率的整体影响**|

**示例**：某日处置 10,000 件、收到申诉 500 件、申诉成功 100 件。
- 以申诉为分母：**20%**（用户诉求得满足的比例）
- 以处置为分母：**1%**（处置中的最终改判占比）

**两者都对，但含义完全不同**。对外汇报与对内考核必须明确写清分母，否则会得出"误伤率 20%"这种严重误导的结论。

### 3.3 误伤率的上下界口径（三池结构）

**误伤率是治理里最难精确测量的指标**——因为你无法穷举"被误伤但没申诉"的样本（M4 §2.2）。申诉按其性质天然分成三个池：

| 池 | 定义 | 信号强度 | 可用于估计什么 |
|---|---|---|---|
| **申诉成功池**| 被处置且申诉成功 | **强误伤信号**| 误伤率的**上界**|
| **申诉失败池**| 被处置且申诉失败 | 多为真违规（也可能证据不足） | 需抽样才能判断 |
| **未申诉池**| 被处置但从未申诉 | **完全未知**| **唯一的盲区**|

**❌ 错误做法**（把申诉池的比例直接外推全量）：

```
全量误伤率 = 申诉成功池的误伤率 × 申诉成功率      ← 统计上不成立
```

**根因：幸存者偏差**。申诉成功的人多半是真被误判（或有强维权动力）的人；未申诉 / 申诉失败的人大概率真违规。**用前者的误伤率代表全体，会严重高估。**

**正确做法（四步）**：

```
Step 1  无偏抽检「申诉成功池」→ 得池内误伤率的点估计
        （前提：离线抽检是该池的无偏代表性样本 → 用分层随机抽样保证）
Step 2  据此估算「申诉成功池内」的误伤绝对值
Step 3  不把这个比例乘到全量上，而把它作为「全量误伤率的上界警戒线」
Step 4  另抽两个池（未申诉池 / 申诉失败池）做人工复核，
        用三池样本占比 × 各自误伤率做加权平均，才得全量估计
```

**可管理的结论形态**：

```
全量误伤率 ∈ [下界, 上界]
   下界：来自随机抽样（成本高，但无偏）
   上界：来自申诉成功池 × 无偏抽检（成本低，且天然偏高）
```

**管理含义**：**日常监控用上界**（变化即可预警），**季度验收用下界**（抽样）。**两者都不需要全量复核。**

### 3.4 申诉指标与相邻模块指标的对照

| 指标 | 分母 | 方向 | 与相邻指标的关系 |
|---|---|---|---|
| **申诉率**| **处置数**| 用户发起 | 与举报率同族（都是相对指标）；但举报率的分母是**曝光数**（M4 §3.1、M9 §2.2） |
| **举报率**| **曝光数**| 用户发起 | 举报指向"该审没审"，申诉指向"不该罚罚了" |
| **申诉成功率**| 申诉数 | 用户诉求满足 | **误伤率的上界代理**，必须先剔除信号污染（§四） |
| **误伤率**| 处置数 | 平台自评 | 与漏放率**必须并列报告**（M4 §3.3） |

## 四、申诉的三类归因（决定一切下游动作）

⚠️ **这一节是 M3 / M4 / M0 三篇共同要求的前置条件**（三篇文档中都已标为"M5 需先完成"）。

| 类型 | 判定特征 | 是否改判 | 信号流向 | 计数归属 |
|---|---|---|---|---|
| **① 判罚错误**（执行问题） | 审核员判错了，规则本身没问题 |  改判 | M3（培训、认知对齐） | 计入**误伤率**|
| **② 规则缺陷**（非执行问题） | **审核员按规则判对了，但规则本身有问题**|  改判 | **M1（规则迭代）**| 不计入误伤，计入**规则缺陷率**|
| **③ 信号污染**（滥用/试探） | 重复申诉、模板化理由、团伙行为 | ❌ 维持 | M9 防滥用 + M6 | 从申诉成功率中**剔除**|

### 4.1 为什么必须分开

> 如果不分类，**申诉成功率就是三者的混合**——它既反映误伤（①），又反映规则质量（②），又被攻击者稀释（③）。
> **混在一起的申诉成功率，作为"误伤先行指标"是不成立的。**

**修正 M4 的表述**（M4 §2.2 原文）：
> 申诉成功率是误伤率的**上界代理**——它偏高（选择偏差），**且必须先剔除"信号污染"类申诉**才可用。

### 4.2 类型 ② 是本模块最被低估的价值

**类型 ② 的特征很特别：审核没错，规则错了。**

| | 类型 ① | **类型 ②**|
|---|---|---|
| 审核员 | 判错了 | **判对了**|
| 规则 | 没问题 | **有问题**|
| 改进对象 | 人 / 模型 | **规则与产品设计**|
| 用户感知 | "平台乱判" | **"平台判得没错，但这个规则不合理"**|

⚠️ **类型 ② 的汇报价值与治理价值都更高**：它说明平台**有能力发现自己的规则问题**，而不是等舆情或监管来指出。

**建议的命名**：把类型 ② 的处理动作称为「**误伤前置定义**」——即**在规则与产品设计阶段就把会产生误伤的边界定义清楚**，而不是等用户申诉才补。

### 4.3 类型 ③ 的识别特征

| 特征 | 说明 |
|---|---|
| **同一主体高频申诉**| 且多集中于同类判罚 |
| **理由模板化**| 文本高度相似，或与判例库高度重合 |
| **申诉成功但行为继续**| 改判后仍反复触发同类判罚 → 试探型 |
| **团伙协同**| 多账号时间聚集 |

→ 这类申诉**不应进入误伤统计**，但**必须进入 M6 的对抗样本库**。

## 五、治理机制：权限、可申诉性与时效

### 5.1 复查权限的独立性（结构性问题）

**核心矛盾**：**申诉不可能由原审核方独立裁定**——那等于让被质疑方做裁判。

| 复查主体 | 优点 | 风险 |
|---|---|---|
| **原审核团队**| 熟悉上下文 | ❌ **自我裁决**，误伤的发现率会被系统性压低 |
| **独立复审团队**| 无利益关联 | 需保证规则理解一致性（否则双审一致率下降） |
| **专职申诉队列**| 专业度高、处理快 | 成本高，只适合高风险案件 |
| **Policy 团队**| 能识别规则缺陷（类型 ②） | ⚠️ **不应由规则制定者裁定个案**（违反 M1 §3.2 的"第三方视角"原则） |

**建议的分工**：

```
受理分流（产品/运营）
   ├─ 常规案件 → 独立复审团队（按规则 + 判例裁定）
   ├─ 高风险/高影响案件 → 专职申诉队列（快车道）
   └─ 疑似规则缺陷（类型②）→ 不改判权限交给 Policy，
                              Policy 只能提交「规则修订提案」，
                              个案改判仍由独立复审团队决定
```

⚠️ **最后一条是本节的要点**：**让 Policy 参与识别规则缺陷，但不给它个案改判权**——既利用了它的专业判断，又避免了"规则制定者同时是结论裁决者"。

### 5.2 可申诉性的边界

**并非所有处罚都可申诉**——但必须**事前明示**：

| 类别 | 可申诉性 | 理由 |
|---|---|---|
| 事实性判定（内容是否违规） |  完全可申诉 | 有客观依据可核 |
| 规则适用性（该规则是否适用本 case） |  完全可申诉 | 类型 ② 的主要来源 |
| 主观尺度（擦边程度的判断） | ⚠️ **有限申诉**| 无客观标准，需说明判定依据 |
| 底线类（法律强制要求） | ⚠️ 可申诉但**改判空间极小**| 平台无裁量权 |
| 证据不可得（内容已删除/过期） | ❌ 可能无法受理 | **需在处置时保留证据副本**|

⚠️ **最后一行是一个容易被忽略的技术约束**：**如果处置时不留存证据副本，申诉阶段就无法复核**。→ 处置动作必须与"证据留存"绑定设计。

### 5.3 时效：分层而不是整体提速

**内在矛盾**：
- 用户诉求是**越快越好**（内容 / 收入已被停掉）
- 但审得越快，**越可能判错**（用户需要时间理解判罚、准备材料）

**解法是分层，而不是全局提速**：

| 分层 | 依据 | SLA 取向 | 配置 |
|---|---|---|---|
| **优先级队列**| 高影响：高曝光、高收入、账号级处罚、权威创作者 | 最短 | 专职队列、双审 |
| **常规队列**| 中等影响 | 标准 | 独立复审团队 |
| **批量/账号级**| 同主体多案 | 合并处理 | 去重后统一裁定 |

**跨域时效锚点（公开材料）**：

| 参照 | 数值 | 来源 |
|---|---|---|
| 商品申诉复杂案件 | 最长 **24 小时**| TikTok Shop【官方自述】 |
| 人审纠错生效（相同物料 MD5 命中） | **约 10 分钟**| 腾讯云文档【官方】 |
| 直播 | **不可回扫**——内容已播出，无法"恢复" | M8 §2.3 |
| **规则从申诉到修订的时延**| **未公开**| — |

⚠️ **直播域的特殊性**：**直播的错误无法"恢复"**（内容已经播出去了）。所以直播申诉的目标不是"恢复内容"，而是 **① 撤销账号/权限处罚 ② 追回收益 ③ 把误伤信号回流去改规则**。这是 M8"不可回扫"在 M5 的投影。

### 5.4 一条极短的回流链路（可直接借用）

**腾讯的做法**【官方文档】：机审纠错后，**MD5 完全相同的物料再送审即按纠错后标签输出，约 10 分钟生效**。

→ **含义**：**申诉的价值不止于"这一条"，而是"这一类"**。这是 §2.7 回流闭环的工程化形态——**把个案结论固化为可复用的判定**。

## 六、申诉体系的三维度校验（与前几篇平行）

| 维度 | 核心指标 | 过程指标 | 说明 |
|---|---|---|---|
| **纠正能力**| **误伤率（§3.3 上下界口径）**、改判率 | 申诉成功率、申诉处理时效、恢复执行完整率 | 是否真的纠正了错误 |
| **信号价值**| **源头修正率**（因申诉而修订的规则数 / 申诉总量） | 三类归因的分布、规则修订提案数、负向判例沉淀数 | **是否把用户不满变成了体系改进**|
| **可持续**| **申诉 ROI**（挽损收益 vs 复审成本） | 申诉量占处置量比、复审人力占比、防滥用拦截率 | 是否可长期运转 |

### 6.1 ⚠️ 恢复执行完整率：一个几乎无人统计的指标

由 §2.4 —— 改判后的恢复动作有四个层级（内容 / 账号 / 资金 / 训练数据）。**"改判了但没恢复完整"是申诉体验最大的落差来源**。

**建议定义**：

```
恢复执行完整率 = 四层恢复动作全部完成的案件数 / 改判案件数
```

### 6.2 源头修正率为什么是本模块的"灵魂指标"

```
只看第一层【补救】的申诉体系 = 成本中心（做得再好也只是"少错一点"）
做了第二层【信号】的申诉体系 = 治理资产（每条申诉都在减少未来的误伤）
```

**"源头修正率"就是区分这两种体系的指标**。它统计的是：**多少条申诉最终变成了规则、审核标准或产品的改进**。

## 七、常见反模式（自查表）

| 反模式 | 表现 | 根因 | 修法 |
|---|---|---|---|
| **申诉率当唯一指标**| 申诉率低就说体验好 | 忽略选择偏差 | 配合申诉成功率 + 抽样审计（§1.1） |
| **原团队复审自己的判罚**| 自我裁决 | 权限设计错误 | 独立复审团队（§5.1） |
| **Policy 直接裁定个案**| 规则制定者兼裁决者 | 违反第三方视角 | Policy 只提修订提案（§5.1） |
| **只改判不归因**| 翻案就结案 | 缺分类流程 | 三类归因（§四） |
| **申诉池直接外推全量**| 用申诉成功池代表全体误伤 | 幸存者偏差 | 三池分层抽样（§3.3） |
| **分母不写明**| "误伤率 20%" | 三种成功率混用 | 口径必须标注分母（§3.2） |
| **改判不恢复完整**| 内容恢复了但账号记录未清 | 恢复动作未清单化 | 四层恢复 + 完整率指标（§2.4） |
| **改判后训练数据不清理**| 负向信号仍污染模型 | 未关联 M3 §6.2 | 从训练样本剔除 |
| **处置不留证据**| 申诉时无法复核 | 证据留存未绑定处置 | 处置即留存证据副本（§5.2） |
| **入口隐蔽**| 藏在三级页面 | 被当作成本 | 入口可达性是诚信问题（§2.1） |
| **直播按点播做申诉**| 想"恢复内容" | 忽略不可回扫 | 撤销处罚 / 追回收益 / 回流规则（§5.3） |
| **申诉当纯成本中心**| 只考核时效与成本 | 缺信号侧指标 | 加源头修正率与 ROI（§六） |
