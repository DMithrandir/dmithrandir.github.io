## 引子：治理最难的不是解决问题

从完整治理链路看，**策略只是最后的"应用落地"环节**。真正难的是前面两件事：

1. **清晰描述问题的全貌**—— 这个乱象到底有多少变体、在哪些场景发生、谁在受害
2. **正确定义问题**—— 它算不算问题？严重到什么程度？平台用什么态度对待它？

这两件事都发生在 **Policy**环节。而"解决问题"（训模型、调阈值、上策略）反而是最好实现的——因为它有明确的目标函数、有成熟的工程手段、有可量化的反馈。

**这就是本文框架的出发点**：把治理看作一条链路，看清每个环节**谁在定义问题、谁在执行、谁在验收、谁在为结果负责**。大模型时代的真正变化不是"模型变强了"，而是**定义问题与解决问题这两件事正在被合并**（见 §九）。

## 一、治理链路总览：四层 + 两个贯穿性机制

```
┌─────────────────────────────────────────────────────────────┐
│  输入层 · 约束从哪来        （§二）                          │
│  法律/监管 · 社会事件 · 平台价值取向 · 用户反馈 · 竞品/行业   │
│                    ↓ 转化为「问题定义」                       │
├─────────────────────────────────────────────────────────────┤
│  中间层 · 治理流水线        （§三 / §五 / §六）              │
│                                                              │
│   Policy ──→ Strategy ──→ Execution ──→ 判罚处置 ──→ 回流    │
│   规则定义    机审策略     人审/机审     分级动作    申诉/复审 │
│   (标签/标准) (模型/阈值)  (审核执行)   (删/限/标/警)         │
│                                                              │
├─────────────────────────────────────────────────────────────┤
│  输出层 · 生态结果          （§四 / §七）                    │
│  违规曝光率 · 举报率 · 误伤率 · 申诉率 · 渗透率 · SLA         │
└─────────────────────────────────────────────────────────────┘
        ↑                                              │
        └──────── 反馈闭环：指标异常 → 回输 Policy ────┘

贯穿性机制 A：对抗与博弈      （§八）
贯穿性机制 B：指标口径与防博弈 （§七）
```

**一句话概括每一层在回答什么**：

| 层 | 回答的问题 | 谁在负责 |
|---|---|---|
| 输入层 | **凭什么管这件事？**| 法务 / 公共事务 / 监管对接 + Policy |
| 中间层 | **怎么把"问题"变成"可执行动作"？**| Policy（定义）→ 策略/算法（编译）→ 审核（执行） |
| 输出层 | **管住了吗？代价是什么？**| 数据分析 + Policy + 业务负责人 |
| 反馈 | **要不要改？改什么？**| Policy 主责，全链路参与 |

⚠️ **这张图最重要的读法**：链路是闭环，但**责任人不是同一个**。"问题定义"由 Policy 负责，"模型效果"由策略/算法负责，"审核质量"由审核运营负责，"生态水位"由业务负责人负责。**跨环节的指标错配是治理失效的头号原因**——用策略指标去考核 Policy，或用审核指标去考核策略，都会逼出各自最优但整体最差的结果。

## 二、输入层：谁有资格定义"什么是问题"

### 2.1 五个来源

| 来源 | 典型触发 | 变更速度 | 可谈判空间 |
|---|---|---|---|
| **法律 / 监管 / 国标**| 《网络安全法》《生成式 AI 服务管理暂行办法》、AIGC 标识办法、各类专项治理 | 慢（月～年） | **低**，硬约束 |
| **社会事件 / 舆情**| 未成年人相关事件、恶性社会新闻、媒体曝光 | **快（小时～天）**| 中，需判断是否被裹挟 |
| **平台价值取向**| 社区公约、生态健康度、品牌调性 | 慢（年） | 高，平台自主决定 |
| **用户反馈**| 举报、不喜欢、负反馈、评论区情绪 | 快 | 高，但需过滤少数敏感 |
| **竞品 / 行业水位**| 同行已治理而我方未治、行业标准提升 | 中 | 高 |

### 2.2 「定义权」是治理的第一性问题

这里有一个容易被跳过、但决定整个体系质量的问题：**平台是被动合规，还是主动定义？**

- **被动合规**：监管说一句，平台写一条规则。结果永远是滞后、补丁式、且难以形成一致的判罚逻辑——**这就是"规则爆炸"的真实来源**（注意：KuaiMod 论文并未使用"规则爆炸"一词，此为该现象的通行描述）
- **主动定义**：平台自己说清"我们是什么样的社区、不要什么内容"，监管要求作为底线被吸收进来

**判断一个平台治理成熟度的最快方法**：看它的规则是"一条条反应式的补丁"，还是"有统一价值取向、新问题可以被推导出来"。后者才可能建立 §五 所说的"可推导的标签体系"。

### 2.3 一个关键区分：法律底线 vs 生态水位

**这两件事的处置逻辑完全不同，混在一起会导致系统性错误**：

| | 法律/安全底线 | 生态水位（质量/体验） |
|---|---|---|
| 例子 | 色情、暴恐、违禁品、诈骗、未成年人保护 | 低质搬运、标题党、诱导互动、擦边、无信息量 |
| 用户偏好 vs 平台态度 | **常冲突**（部分用户就是喜欢擦边） | **通常一致**（用户也不喜欢低质） |
| 举证责任 | 平台举证"已尽力" | 平台举证"有改善" |
| 能否个性化 | **不能**，必须统一标准 | **可以**，不同用户容忍度不同 |
| 主要指标 | 阻断率、漏放率（**绝对合规导向**） | 低质 VV 占比、举报率（**相对水位导向**） |

**这条区分直接决定指标设计**：底线类看"漏放率/阻断率"，水位类看"占比/渗透率"。用错了就会出现"底线上线 99.9% 但仍被通报"或"水位治理把有效内容一起压掉"。

### 2.4 处置光谱：不是只有"删"和"不删"

规则写完后，必须先决定**处置动作**，再谈技术实现。这是 Policy 最常被低估的产出：

| 处置 | 适用 | 技术实现 | KuaiMod 的做法 |
|---|---|---|---|
| **硬阻断**| 违法、严重危害 | 拦截不进审核队列 | "explicitly violate laws or pose severe harm 的严格过滤" |
| **限流/不推荐**| 违规但不违法 | 移出推荐池 | "videos identified as violative are directly removed from promotion" |
| **个性化**| 成人可看、未成年不可 | 判定结果作为推荐特征 | 嵌入推荐特征，**DAU +0.028% / 总 AUT +0.063%**|
| **标注/提示**| AIGC、争议事实、可能引起不适 | 打标 + 前端提示 | 快手 104 万条视频加 AI 标识 |
| **预警/干预**| 直播演绎诱导下单 | 弹窗警告/遮罩/断播 | 快手"剧本炒作"举报率 −61% |

⚠️ **常见错误**：把"限流"当成"轻量删除"来用。限流是**保留内容但改变分发**，必须和推荐系统协商，且要监控"是否把有效性内容一起限掉"。

## 三、中间层：治理流水线的五个环节

### 3.1 环节一：Policy（规则定义）

- **产出物**：问题定义 + 标签体系 + 规则/标准文本 + 处置建议 + 指标口径
- **核心问题**：问题全貌描述清楚了吗？标签体系正交吗？机审判得动吗？
- **详见**：[M1 · 规则运营](/governance/03-policy/)

### 3.2 环节二：Strategy（策略编译与落地）

- **产出物**：机审模型 + 阈值策略 + 级联路由 + 处置策略 + 回扫任务
- **核心问题**：给定误伤约束下能自动处理多少？单件成本多少？新规多久全量生效？
- **核心权衡**：阈值不可能统一，必须**按风险类分别标定**（RADAR 实测线上正例率从 9.0%（虚假互动）到 25.5%（低质内容））
- **详见**：[M2 · 策略与机审模型](/governance/04-strategy/)

### 3.3 环节三：Execution（审核执行）

- **产出物**：人审结论 + 机审判定 + 质检结果 + 申诉处理
- **核心问题**：认知对齐了吗？效率与质量平衡吗？灰度抽检够吗？
- **本系列待写模块**：Execution（审核运营 / 质检体系）

### 3.4 环节四：判罚处置

- **产出物**：内容级处置 + 账号级处置 + 商家级处置 + 公示/通知
- **核心问题**：单条 vs 账号 vs 团伙的处置梯度怎么定？时效要求多少？
- **一个高价值细节**：**腾讯的纠错名单机制**——机审纠错后，**MD5 完全相同的物料再送审即按纠错后标签输出，约 10 分钟生效**。这是"人审回流到机审"最短的一条链路，成本极低却常被忽略。

### 3.5 环节五：回流与申诉

- **产出物**：申诉判定 + 误伤复盘 + 训练数据 + 规则修订提案
- **核心问题**：申诉是"用户权益通道"还是"质量信号源"？两者要同时用
- **高价值做法**：淘天称每次抽检后 AI 自动总结"哪些判对了、哪些漏了"写回知识库；KuaiMod 的 RLUF 只取"模型判定与用户感知不一致"的争议样本（**数百条即可天级更新**）

### 3.6 跨环节的两个隐性契约

1. **Policy → Strategy 的契约是"可判定性"**：每条规则必须能对应具体证据（画面/文本/行为），否则机审无法执行、人审只能靠自由裁量
2. **Strategy → Policy 的契约是"反馈质量"**：模型必须回报"哪些规则下误伤率异常高"，这是规则该改的信号，而不是模型该调阈值的信号
   - ⚠️ 这个信号经常被误处理：把"规则表述模糊导致的误伤"当成"模型不准"去调阈值，结果阈值调松了、底线漏放了

## 四、输出层：生态结果该怎么量

### 4.1 三层指标架构

| 层 | 指标 | 用途 | 特征 |
|---|---|---|---|
| **合规层**| 漏放率、阻断率、处置时延 | 对监管交代 | **绝对导向**，不可谈判 |
| **生态层**| 违规曝光率（VVR）、低质 VV 占比、举报率、渗透率 | 对业务交代 | **相对导向**，看趋势与结构 |
| **成本层**| 误伤率、申诉率与申诉成功率、人审量、单件成本、SLA | 内部效率 | **约束导向**，决定自动化天花板 |

### 4.2 国际平台的可比口径

- **YouTube VVR（Violative View Rate）**：自 2020Q4 起按季披露，衡量"违规内容获得的观看量占比"，公开历史值长期在 **0.1%~0.2% 量级**—— 这是**目前最值得借鉴的单一生态指标**，因为它以"观看量"为分母，天然抗"多发内容摊薄"式博弈
- **TikTok**：披露"自动化检出占比"（2026Q1：下架 1.84 亿条，**96.7% 由自动化检出**、主动处置率 99.3%、94.4% 于 24 小时内下架）—— 但这个比率**分母口径未公开**，只能看趋势不能横向比较
- **Meta**：透明度口径为 **prevalence（渗透率）+ 主动发现率**，而非"删了多少条"

### 4.3 ⚠️ 国内平台公开口径的三个陷阱

1. **"漏放率 0.1%"这类数字分母不可知**。快手电商报告称"整体风险漏放率降至 0.1%"，但未披露风险样本的统计口径、抽样方式与置信区间
2. **"举报率下降 X%"必须绑定作用域**。KuaiMod 的 −20% 只针对**举报 ≥5 次的视频**这一高风险候选池，不是全量内容
3. **自述比率与论文指标不可并列**。Amazon 99.9%、TikTok Shop 99.5%、快手 0.1% 都是平台自述，**不可与论文的 F1/召回率直接比较**

**结论：对外引用用官方口径，对内考核必须自建口径。**用外部披露数字做内部 KPI 是治理体系里最常见的一类事故。

### 5.1.1 审核产品三兄弟：召回 / 举报 / 申诉（三套独立系统）

**由用户定义**：**召回、举报、申诉是三套独立的系统**，各有独立的产品与团队。本系列因此把它们拆成三个模块：

| | **召回**| **举报**| **申诉**|
|---|---|---|---|
| 模块 | **M3**| **M9**| **M5**|
| 发起方 | 平台 | **用户（消费者）**| **用户（被处置方）**|
| 本质 | **筛选**| **发现**| **纠错**|
| 回答什么 | 全量内容里哪些该进审核 | 哪些内容用户认为是问题 | 哪些处置用户认为判错了 |
| 输入 | 全量内容 + 各类信号 | 用户的负反馈动作 | 用户的翻案请求 |
| 输出 | 待审队列（按优先级） | 举报工单 + 异常信号 | 改判/维持 + 规则反馈 |
| 成本结构 | 人力预算下的召回率最大化 | 无效举报稀释有效送审 | 复核成本 vs 挽损收益 |
| 主导角色 | 算法 / 策略 | **审核产品**| **审核产品**|
| 主要接口 | → M2 策略、M1 规则缺口 | → M0 风险感知、M1 规则迭代 | → M1 规则迭代、M4 误伤口径 |

**一句话区分**：
> **召回是平台主动找要审的，举报是用户告诉你该审的，申诉是用户告诉你不该罚的。**

⚠️ **为什么必须分开**：
> **平台侧信号的输入是"内容"，用户侧信号的输入是"人"。**
> 前者只需要内容理解能力；后者还要处理**用户动机**（真实反感 / 恶意 / 试探 / 维权），并且**直接决定用户对平台的信任感**——举报入口的可用性、申诉结果的透传，都是产品问题，不是模型问题。

**闭环关系**：`M3 召回 → 审核 → M9 举报（用户反馈）→ M0 发现 → M1 定义 → M2 实现 → 审核 → M5 申诉（用户纠错）→ M1/M3 修正`

> **为什么 M0 编号在最前**：**发现问题在时间上先于定义问题**。整个链路的最前端不是 Policy，而是"从异常中发现候选问题"——Policy 处理的是"已经知道有问题"之后的判断。

### 5.2 依赖关系（哪些模块必须先想清楚）

```
M0 Risk Sensing ──提供「候选问题单」──→ M1 Policy ──「可判定性」──→ M2 Strategy ──「判定置信」──→ M3 Execution
     ↑                                    ↑                                ↓                        │
     │                                    │                                ↓                        │
     │                                    └──── M4 Metrics（口径贯穿全链路）─────────────────────────┤
     │                                                                                              │
     └──────────────── M5 Feedback ←──────── M3 的申诉与质检结果 ──────────────────────────────────┘

M6 Adversarial 与 M0/M1/M2 强耦合（对抗样本库是"发现时延"的黑产侧锚点）
M7 Org 由 M0~M5 的协作契约倒推
M8 Domain 是 M0~M7 在两个治理域上的投影
```

**链路的一个关键性质**：M0 是**唯一在问题形成规模之前就能介入的环节**。M1~M5 处理的是已发现的问题；只有 M0 决定"问题被发现的时点"，而发现越及时、介入越前置、风险越可控。

⚠️ **M0 的误报成本记在 M1 账上**：候选问题成案率若只有 10%，意味着 M1 有 90% 产能在处理噪声。所以 M0 的校验指标（§本篇 §六）必须纳入考核。

### 5.3 为什么先写 Policy

1. 它是链路的上游——**Policy 定义了，后面才有可优化的目标函数**
2. 它是最容易被误解的岗位（"只是写标准的工具人"），澄清价值密度最高
3. 它的产出物（标签体系、指标口径）**是全链路共用的接口**，先定接口再定实现

## 六、一条贯穿全篇的经验规则：治理的「接口思维」

治理论文和分享里最容易被忽略、但对从业者最有价值的一点：**治理链路的质量上限由接口质量决定，而不是由单点技术决定**。

| 接口 | 上游给什么 | 下游需要什么 | 好接口的标准 |
|---|---|---|---|
| 监管 → Policy | 法律条文、监管要求 | 可执行的问题定义 | **能翻译**：法条 → 具体场景与证据 |
| Policy → Strategy | 标签体系、标准文本 | 可判定的分类目标 | **可判定**：每条规则对应具体证据 |
| Strategy → Execution | 模型判定 + 置信度 | 可直接采信/需复核的结论 | **可校准**：置信度有可靠性语义 |
| Execution → Feedback | 人工结论 | 可复用为训练/规则信号 | **可归因**：判错要能区分"规则问题"还是"能力问题" |
| Feedback → Policy | 误伤与漏放复盘 | 规则修订依据 | **可追溯**：指向具体条款而非笼统"不准" |

⚠️ 其中 **"置信度可校准"**是最容易被跳过的一步：不同模型的原始置信度**不可比**，必须先校准到同一把尺子，才能统一回答"接受早停 / 升级强模型 / 融合输出"。CAUC（[arXiv:2609.11446](https://arxiv.org/abs/2609.11446)）的做法是独立校准每个模型的置信度，在六个语言基准上相对"只用强模型"**平均相对精度 +1.9%**，同时**省掉约 47% 的强模型调用**——**校准本身就是收益**。

## 七、贯穿性机制 B：指标口径的严谨性与防博弈

**这一节建议单独成篇（M4），但必须在总纲里点名，因为它决定了前面所有模块的考核有效性。**

### 7.1 一个指标的定义必须包含五项

以最常被滥用的「低质 VV 占比」为例：

| 要素 | 必须明确 | 不明确的后果 |
|---|---|---|
| **分子**| 哪些视频算低质？按谁的定义？ | 松紧变化直接改变结论 |
| **分母**| 全部 VV？还是仅推荐流 VV？ | 站内 vs 站外口径差数倍 |
| **时间窗**| 当日？7 日？是否含老内容回扫？ | 回扫上线会让指标突变 |
| **加权**| 是否分用户、分品类、分场景加权 | 头部品类会主导结果 |
| **口径版本**| 什么时候改过口径？ | 跨期比较直接失效 |

### 7.2 三类抗博弈设计

1. **举报率 vs 举报绝对数**：**举报率是相对指标，天然抗博弈**——限流会让分子分母等比下降（这点是相对指标的核心优势）。但如果 KPI 是"举报条数"，就会出现"多发内容摊薄比率"或"干脆减少曝光"的畸形最优
2. **单指标必被博弈，要用指标三元组交叉验证**：
   - 效果指标（举报率、低质 VV 占比）↑
   - 成本指标（误伤率、申诉成功率）↑
   - 规模指标（自动处置量、覆盖率）↑
   - **三者同时改善才算真改善**；只动一个，通常是在搬移问题
3. **口径独立**：评估低质水位应引入**第三方视角**，避免 Policy **既是规则制定者又是结论裁决者**（这是工作笔记里最精准的一条洞察）

### 7.3 成本侧必须显性化

治理指标如果只报收益不报成本，必然导致"越治越狠"。必须同时跟踪：
- **误伤率**：UNIVID 把误伤从基线降 **−37.0%**（与其漏放 −42.7% 并列报告，这个并列本身就是成熟度标志）
- **跨域误伤**：SIRF 作树模型裁决层**多找回 20% 误罚样本**、跨域**误罚 −70%**
- **人力成本**：Amazon 商品质检**专家工时 5.1 小时/属性 → 3 分钟（−99%）**
- **商家/创作者侧成本**：商品规则变更会**反向阻塞已发布商品，需全生命周期回扫**—— 这条成本常被完全忽略，却直接落在 GMV 上

### 7.4 时效指标：治理体系最稀缺的公开数字

**"新规上线到全量生效需要多久"**是工业界几乎不公开、但业务上最关键的指标。目前能找到的间接锚点：

| 锚点 | 数值 | 来源 |
|---|---|---|
| 人审纠错回流生效 | **约 10 分钟**（MD5 命中即改判） | 腾讯云文档 |
| 规则天级更新 | **数百条数据 / 天级**| KuaiMod |
| 判例库新增 → in-context 生效 | 无需重训（10 万条判例库） | UNIVID |
| 政策内化（CPT）改动成本 | 需重训（70M token CPT） | SIRF |
| 商品全生命周期回扫 | **未公开**（仅知"需回扫"） | 淘宝技术复盘 |

## 八、贯穿性机制 A：对抗与博弈

治理不是静态优化问题，而是**与主动规避者的持续博弈**。这决定了三条设计原则：

### 8.1 规避是常态，不是异常

- **形态**：谐音、形近字、分词、委婉语、裁图、emoji、零宽字符、结构化模板、AIGC 低成本风险样本
- **证据**：快手安全团队明确指出底线风险"**仅占千分之几流量**"且对抗变异强；EVADE-Bench 评测 26 个 LLM/VLM，**SOTA 仍频繁误判**，而**更清晰的规则分档显著提升预测一致性、降低误判**
- **原则一：规则层级越清晰，模型对抗鲁棒性越强**—— 这直接把 Anti-adversarial 与 Policy 的质量绑在一起

### 8.2 护栏自身就是攻击面

- **AdvJudge-Zero**（Unit 42）：自动化 fuzzer 用**低困惑度的无害 token**（markdown 符号、列表标记、结构短语）操纵 allow/block 的 **logit gap**放行违规内容，**完全黑盒**
- **Emoji Attack**（ICML 2025）：emoji 插入同样可绕过 Judge LLM
- **MM-SafetyBench**：12 个 SOTA 多模态模型即便底座已安全对齐，仍可被**与 query 相关的图像**攻破
- **原则二：审核判定链路本身要有红队机制与输入规范化**，不能假设"模型对齐过了就安全"

### 8.3 攻防节奏要写到 SLA 里

- 快手直播治理给出"**识别时效从分钟级降至秒级**"，并对应"低俗直播举报率同比 −55%"
- 黑产规模化攻击是一次**容量与响应**的联合考验，而不是单纯的"模型准不准"
- **原则三：时效是一等指标**。规则再好，晚 2 小时生效就等于没有

## 九、大模型时代：治理范式的三个真实变化

**这是本系列与外部技术文章的最大连接点，也是"定义问题与解决问题正在合并"的具体体现。**

### 9.1 变化一：Policy 的产出物变了 —— 从"规则文本"到"标签体系 + 指标口径 + 判例"

| | 传统 | 现在 |
|---|---|---|
| Policy 核心产出 | 规则文本 + case 举例 | **可推导的标签体系**+ **指标口径**+ **判例库**|
| 规则与代码的关系 | 规则 → 人工翻译成策略 | 规则 → 大模型自动编译为标签树/检查项 |
| 新风险上线 | 写规则 → 标注 → 训模型（滞后） | 语义热插拔 / 判例 in-context（天级甚至即时） |

**证据**：
- 快手安全大模型用大模型把"内容描述 → 结构化标签树"，并做**标签-规则条款自动匹配与冲突校验**；开集 Tagging 让新类**只需一条文本描述即可零样本扩展（"语义热插拔"）**
- 淘宝 SPU 项目用大模型推导属性类型与品类定义，经小二审核后**沉淀为正式规则**
- 小红书 SIRF 用 **EntiGraph + MAGA 改写 + 账号级 CoT 零人工标注**合成政策语料（约 70M CPT token）

### 9.2 变化二：Policy 与 Strategy 的边界正在模糊 —— 规则必须选"住在哪里"

这是本系列最需要建立的**新判断力**。规则不再只有"文本形态"，它必须被决定**注入到哪个位置**：

| 注入位置 | 代表 | 变更速度 | 代价 | 适合的规则类型 |
|---|---|---|---|---|
| **Prompt**| Hi-Guard（政策进 Prompt + GRPO 软边界奖励） | 秒级 | 吃上下文、延迟高 | 变更频繁、需可解释 |
| **检索库**| Class-RAG 类 | 热修复 | 检索延迟长期累积 | 长尾多、需引用溯源 |
| **模型权重**| SIRF（CPT 70M tokens） | 需重训 | 高 | 稳定、样本足、量最大 |
| **判例库**| KuaiMod 的 common law；UNIVID 10 万条判例 | **天级**| 判例运营成本 | 长尾争议、需共识 |

**关键判断（可直接用于决策）**：

> Policy 在写规则时，**必须同时决定这条规则的"居住地"**。而选择依据不是技术先进性，而是**规则的变更频率 × 证据的具体程度**：
> - 变更慢 + 证据具体 → 权重（CPT/微调）
> - 变更快 + 证据具体 → 检索库 / Prompt
> - 变更快 + 证据抽象 → 判例库
> - 变更慢 + 证据抽象 → **这条规则不该存在，先回去定义问题**

⚠️ **"证据抽象"不是策略问题，是 Policy 问题**。这是 Policy 从业者在大模型时代最重要的自我要求：**写不出一条规则的具体证据，就不该把问题转给策略团队**。

### 9.3 变化三：组织角色重构 —— 运营岗正在变成"模型教练"

- **快手磁力引擎**明确表述"**部分一线审核员实际上已经被大模型替换掉了**"；运营岗三级跃迁：**规则表达式 → Prompt Engineer → RAG 运营 → 模型教练**（2025 Q3 起把 SFT 做成线上化平台，**由运营直接运维模型 pipeline**）
- **组织指标已量化到 Token**：日均 Token 消耗 1 亿、推行 Token ROI 与 Skills 贡献度考核
- 反面提醒：**Agent = 10% 的 AI + 90% 的软件工程**（快手安全团队引用 Rakesh Gohel 冰山模型）——治理 Agent 化的瓶颈在工程与流程，不在模型

**对从业者的含义**：Policy 的能力要求从"写得清楚"升级为"**写得清楚 + 能被机器执行 + 能被度量**"。会写标准只是入场券，能把标准变成可判定、可度量、可迭代的资产，才是大模型时代的护城河。

## 十、内容治理 vs 商品治理：同构与分叉

| 维度 | 内容治理（短视频/社区/直播） | 商品治理（电商/广告） |
|---|---|---|
| 治理对象 | 单条内容 | **有生命周期的商品/SKU**|
| 主要风险 | 违法、低质、擦边、未成年人 | 违禁品、假冒侵权、虚假宣传、错放类目 |
| 硬约束 | 传播速度快 | **规则变更会反向阻塞已发布商品，需全生命周期回扫**|
| 特殊结构层 | 评论区、直播实时流 | **类目/属性/SPU 结构层**（最隐蔽，却直接影响搜索召回与比价） |
| 举证方式 | 平台内部 | **商家工单 + 申诉 + 资质库**|
| 关键指标 | VVR、低质 VV 占比、举报率 | 错放漏放率、拦截量、专家工时、GMV 影响 |
| 主要收益证据 | UNIVID 漏放 −42.7%/误伤 −37.0% | Amazon auto-prompt：P/R +8~10%、**专家工时 −99%**|
| 标杆数据 | KuaiMod：48×4090 / QPS 6.81 / 60 万条/日 | 淘天生鲜：微调后 79%→90%，**双卡 L20 约 10 QPS**|

**共性**：都遵循"**规则引擎 + 关键词/OCR/以图搜图 → 小模型高 QPS 首筛 → 大模型兜底 → 人工**"的级联漏斗（与推荐系统的召回-排序同源）。

**最关键的差异**：商品有"**已发布状态**"。内容违规删掉就结束了，商品违规需要**回扫全量在售 + 通知商家 + 阻断交易 + 处理库存**，所以商品治理的瓶颈不在识别率，而在**规则变更效率与全生命周期回扫能力**。

## 十一、卡片速查

### 11.1 四个核心判断

1. **治理最难的是定义问题，不是解决问题**。策略只是最后的应用落地环节。
2. **Policy 的产出不只是标准文本，还有标签体系与指标口径**——后两者是全链路的接口，接口质量决定治理上限。
3. **规则必须选"居住地"**（Prompt / 检索库 / 权重 / 判例库），选择依据是**变更频率 × 证据具体程度**；证据抽象是 Policy 的问题，不是策略的问题。
4. **指标三元组交叉验证**（效果 + 成本 + 规模），单指标必被博弈。

### 11.2 指标口径字典（可直接复用）

| 指标 | 建议口径 | 抗博弈要点 |
|---|---|---|
| VVR（违规曝光率） | 违规内容观看量 / 总观看量 | 以观看量为分母，抗"多发摊薄" |
| 低质 VV 占比 | 需定义分子集合、分母范围（站内/推荐流）、时间窗、加权 | 口径变更必须版本化 |
| 举报率 | 举报数 / 曝光数（**分母是曝光，不是内容数**） | 相对指标，限流等比下降 |
| 举报有效率 | 判定成立的举报 / 总举报 | 防止用户滥用举报 |
| 漏放率 | 事后抽查发现的违规 / 抽查总量 | 抽样方式与置信区间必须公开 |
| 误伤率 | 申诉成功 + 质检推翻 / 处置总量 | **必须与漏放率并列报告**|
| 双审一致率 | 二次审核结论一致占比 | 是**规则可判定性**的核心诊断指标 |
| 新规生效时延 | 规则定稿 → 全量生效 | 工业界最稀缺的公开数字 |
| 单件审核成本 | 含算力 + 人力 + 纠纷成本 | 决定自动化天花板 |

### 11.3 引用时必带的限定（来自技术层调研）

1. 快手 KuaiMod 的"举报率 −20%"**只适用举报 ≥5 次的高风险候选池**
2. **"20%" 与 "26%/24%" 是两个口径**（后者是快手多模态大模型体系整体）
3. **主站安全算法中心 vs 商业化/磁力引擎是两支团队两套模型**，数字不可互代
4. **KuaiMod 基座是 YuanQi，不是 Keye-VL**
5. 平台自述比率（Amazon 99.9%、TikTok 96.7%、快手 0.1%）**口径与分母未公开，不可与论文指标并列**
