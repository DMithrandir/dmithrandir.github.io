## 〇、先纠正一个前提误区

**❌ 误区**：治理是技术问题——模型够强、规则够全，组织怎么设不重要。
**实情**：**治理失效的多数根因不是技术，而是跨环节的接口断裂与指标错配。**

**总纲 §一 已指出**：链路是闭环，但**责任人不是同一个**——

| 环节 | 负责什么 | 常见错配 |
|---|---|---|
| M0 发现 | 问题定义 | 用策略指标考核发现能力 |
| M1 规则 | 可判定性 | 用审核指标考核规则质量 |
| M2 策略 | 自动处置效率 | 用审核量考核策略效果 |
| M3 召回 / 审核 | 覆盖与认知对齐 | 用召回率考核审核质量 |
| M4 指标 | 口径 | **让被考核方设计考核标准**|
| M5 申诉 | 纠错 | 让原审核方裁定自己的判罚 |
| M9 举报 | 用户信号质量 | 只考核处置时效 |

> **用策略指标考核 M1、用审核指标考核 M2，各自都会最优，但整体最差。**

**本篇的核心命题**：

> **组织设计的本质，是给链路的每个接口指定唯一责任人，并让每个人的"最优"与整体的"最优"同向。**

## 一、治理链路的角色地图

按 M0~M9 展开，每个模块的**主导角色、核心产出、关键能力**：

| 模块 | 主导角色 | 核心产出 | 关键能力 | 一手参照 |
|---|---|---|---|---|
| **M0 风险感知**| 数据分析 / 策略运营 | 候选问题单 | **问题嗅觉 + 多维下钻 + 定性调研**| 抖音反网暴的识别+研判双轨 |
| **M1 Policy**| 规则运营 | 标签体系、标准、判据 | **问题定义 + 可判定性设计**| 快手标签体系三步法 |
| **M2 Strategy**| 算法 / 策略 | 模型、阈值、路由 | **约束下最优 + 成本工程**| 快手"7B 对标 32B/72B" |
| **M3 召回/审核**| 审核运营 | 待审队列、人审结论、质检信号 | **认知对齐 + 效能平衡**| 双审一致率、灰度率 |
| **M4 Metrics**| 数据 + 指标 owner | 指标字典、实验设计 | **抗博弈口径设计**| VVR、三种申诉成功率 |
| **M5 申诉**| 审核产品 | 改判、误伤口径、回流信号 | **权限正义 + 归因分类**| 腾讯 10 分钟纠错回流 |
| **M6 对抗**| 安全算法 / 风控 | 对抗样本库、红队 | **攻防节奏 + 成本结构**| AdvJudge-Zero 类红队 |
| **M9 举报**| 审核产品 | 举报工单、异常信号 | **信号质量 + 前端设计**| 抖音 vs 视频号形态差异 |
| **M8 分域**| 各域负责人 | 分域方法论 | **跨体裁迁移判断**| 直播"不可回扫" |

⚠️ **一个关键观察：M5 与 M9 由同一类角色（审核产品）主导**。
原因已写在 M9 §1.1：**举报链路的最后一段就是"创作者申诉"**——它们串在同一个产品里，且都处理"用户侧信号"（输入是"人"而非"内容"，见 M9 §2.8）。

## 二、四类角色的能力模型与演进

### 2.1 四类角色的能力要求

| 角色 | 核心能力 | 容易被误认为的核心能力 |
|---|---|---|
| **规则运营（M1）**| **问题定义 + 可判定性设计**（把抽象问题变成有证据的判断） | ❌ "会写标准文档" |
| **策略/算法（M2）**| **约束下的最优分配**（成本、吞吐、误伤三条硬约束） | ❌ "把准确率做上去" |
| **审核运营（M3）**| **认知对齐 + 度量有效性**（提供真值，而非只提供产能） | ❌ "处理量与人效" |
| **审核产品（M5+M9）**| **用户侧信号设计 + 权限正义**| ❌ "做前端交互" |

### 2.2 岗位的三级跃迁（快手商业化风控的一手口径）

【官方】王东旭（AICon/QCon）：运营岗演进路径——

```
规则表达式  →  Prompt Engineer  →  RAG 运营  →  模型教练
   │              │                  │            │
写规则文本      写规则提示词      运营知识库    运营模型 pipeline
```

**关键事实**：**2025 Q3 起把 SFT 做成线上化平台，由运营直接运维模型 pipeline。**

⚠️ **这条演进的本质**：
> **规则运营的交付物从"文本"变成了"可运行的资产"。**
> 对应 M1 §7.1 的判断——**Policy 必须决定规则"住在哪里"**（Prompt / 检索库 / 权重 / 判例库），而"模型教练"就是这件事的岗位化。

**同一来源的其他组织指标**：

| 指标 | 数值 |
|---|---|
| 代码 AI 自动入库率 | **>35%**|
| 智能标注自动化率目标 | **≥70%**|
| 日均 Token 消耗 | **1 亿**|
| 考核口径 | **Token ROI + Skills 贡献度**|

⚠️ **"日均 Token 消耗 1 亿"值得单独看**：这是一条**罕见地把 AI 使用量写进组织指标**的公开案例——它说明治理组织已经开始**用量化方式管理 AI 投入**，而不只是管理产出。

### 2.3 产能身份被替代、度量身份被强化

【官方】快手磁力引擎明确表述：**"部分一线审核员实际上已经被大模型替换掉了。"**

**但这不等于"审核岗位消失"**——M3 §〇 已给出结构性判断：

| 身份 | 作用 | 趋势 |
|---|---|---|
| **① 产能**：批量判定 | 消耗人力出结论 |  **正在被大规模替代**（智能标注自动化率目标 ≥70%） |
| **② 度量**：**提供人审真值**| 校准机审、评估规则、验收策略 | ❌ **不可替代**——机器无法自己证明自己对 |

**推论**：
> **人审的价值锚点从"产能"转向"度量"。**对应岗位能力要求从"判得快、判得准"转向
> **"能设计抽检方案、能产出可校准的真值、能开出规则/模型反馈单"**。

## 三、跨环节的协作契约（本篇最实用的一节）

**每个接口都需要一份明确的契约**——规定交出去什么、下游需要什么、好接口的标准。

| 接口 | 上游交付 | 下游需要 | 契约标准 | 违约后果 |
|---|---|---|---|---|
| **M0 → M1**| 候选问题单 | 可定义的问题 | **可定义**：能推出规则 | 规则产能处理噪声 |
| **M1 → M2**| 标签 + 判据 + 处置建议 | 可判定的目标 | **可判定**：每条规则对应具体证据 | 算力拟合模糊目标 |
| **M2 → M3**| 判定 + 置信度 | 可采信/需复核 | **可校准**：置信度有可靠性语义 | 阈值无法统一 |
| **M3 → M5**| 人工结论 | 可复用为信号 | **可归因**：能区分"规则问题"还是"能力问题" | 申诉统计失真 |
| **M5 → M1**| 三类归因结果 | 规则修订依据 | **可追溯**：指向具体条款 | 申诉白做 |
| **M9 → M0**| 异常信号 | 候选问题 | **可归因**：三类归因分类完成 | 信号被当工单消耗 |
| **M6 → M1/M2**| 对抗样本 | 回归测试集 | **可回归**：每次变更后必测 | 修 A 坏 B |

### 3.1 三个最容易断裂的契约

**① "置信度可校准"（M2 → M3）**

不同模型的原始置信度**不可比**，必须先校准到同一把尺子，才能统一回答"接受早停 / 升级强模型 / 融合输出"。
**证据**：CAUC（[arXiv:2609.11446](https://arxiv.org/abs/2609.11446)）独立校准每个模型置信度，在六个语言基准上相对"只用强模型"**平均相对精度 +1.9%**，同时**省掉约 47% 的强模型调用**。
→ **校准本身就是收益**。这个契约的违约代价是"**级联无法设统一阈值**"。

**② "可归因"（M3/M9 → M1）**

必须能区分**"审核判错"（执行问题）**与 **"审核判对但规则有问题"（非执行问题）**。
**证据**：M5 §四的三类归因。**M5 §5.1 明确要求 Policy 只提修订提案、不裁定个案**——既用其专业判断，又避免"规则制定者兼结论裁决者"。
→ 违约代价：**申诉统计失真，规则迭代失去主要输入**。

**③ "评估口径独立于优化目标"（贯穿 M0~M6）**

M1 §3.2 的原始表述：**避免 Policy 既是规则制定者又是结论裁决者。**
**工程化做法**：
- 低质水位由**独立团队或第三方抽检**评估
- Policy 提供定义与场景拆分，**不提供结论**
- 上线前后对比实验由**非 Policy 团队**执行

## 四、必须制度化的三个隔离

**"谁评估谁"是组织设计的核心问题**。治理链路里有三处天然的利益冲突，必须用制度隔离：

| # | 冲突 | 错误做法 | 正确做法 | 依据 |
|---|---|---|---|---|
| **1**| **评估低质水位**| Policy 自己评估改善 | 独立团队 / 第三方抽检评估 | M1 §3.2 |
| **2**| **复审申诉**| 原审核团队复审自己的判罚 | 独立复审团队；高风险走专职队列 | M5 §5.1 |
| **3**| **规则缺陷的裁定**| Policy 直接裁定个案 | Policy **只提修订提案**，个案仍由独立复审裁定 | M5 §5.1 |

⚠️ **三处冲突的共同结构**：**让被质疑方做裁判**。
> 它的危害不是"判错"，而是**误伤的发现率被系统性压低**——因为没人愿意证明自己错了。

## 五、组织设计的校验三维度

| 维度 | 核心指标 | 过程指标 | 说明 |
|---|---|---|---|
| **接口完整**| **每个接口有唯一责任人**；契约标准可验收 | 跨环节返工率、契约违约事件数 | 是否存在"三不管"地带 |
| **指标同向**| **各角色的考核指标是否互相冲突**| 指标错配清单、跨团队争议数 | 局部最优是否等于整体最优 |
| **角色有效**| **度量身份是否被强化**（而非只保留产能身份） | 人审真值产出量、反馈单数、模型教练占比 | 组织是否在向"资产化"演进 |

### 5.1 "接口完整"的自检方法

**用一张表逐个接口问三个问题**：

| 问题 | 若答不出 |
|---|---|
| 这个接口**交出去什么**？ | 产出定义不清 |
| 下游**需要什么形式**？ | 接口形态错配 |
| **谁负责**验收？ | 三不管地带 |

### 5.2 "指标同向"的检查方法：三元组对齐

M4 §5.2 提出的"指标三元组"（效果 + 成本 + 规模）**也应跨角色对齐**：

| 角色 | 是不是只考核了对自己有利的那一项？ |
|---|---|
| M2 策略 | 若只考核"自动处置量" → 会放宽阈值 |
| M3 审核 | 若只考核"人效" → 会降低判定质量 |
| M5 申诉 | 若只考核"处理时效" → 会草率维持原判 |
| M9 举报 | 若只考核"处置时效" → 会不区分举报质量 |

⚠️ **每个角色只看一个指标，都会做出对自己最优、对整体最差的选择。**

## 六、常见反模式（自查表）

| 反模式 | 表现 | 根因 | 修法 |
|---|---|---|---|
| **指标错配**| 用策略指标考核规则、用审核指标考核策略 | 未按接口定义考核 | 按 §三 契约表逐项对齐 |
| **自己评估自己**| Policy 报水位改善 | 缺第三方视角 | 独立评估（§四） |
| **自己复审自己**| 原审核团队裁申诉 | 权限设计错误 | 独立复审（§四） |
| **规则制定者兼裁判**| Policy 直接改判个案 | 权限混淆 | 只提修订提案（§四） |
| **人审只考核产能**| 忽略度量身份 | 价值锚点错位 | 加真值产出、反馈单指标（§2.3） |
| **角色边界按工具划分**| 按"谁用哪个模型"分工 | 应按接口划分 | 按链路接口定责（§三） |
| **举报与申诉分给两个产品团队**| 信号口径不一致 | 未识别同一攻击面 | 同一类角色主导（§一） |
| **无红队编制**| 等黑产当红队 | 缺例行机制 | 建红队（M6 §五） |
| **AI 投入无量化**| 说不清 AI 用了多少 | 缺组织指标 | 参考 Token 消耗/ROI（§2.2） |
