## 〇、先纠正一个前提误区

**❌ 误区**：指标是"中立的度量工具"，选一个能把改善讲清楚的就是好指标。
**实情**：**指标一旦被用于考核，它就不再是度量工具，而是一份行为契约**——它规定了整个组织会朝哪个方向用力。

**这个判断的分量，用治理场景的反例说明最清楚**：

| 如果 KPI 是… | 组织会理性地做出… | 结果 |
|---|---|---|
| 违规内容**处理条数**| 多发内容摊薄比率 / 扩大判定口径 | 删除量涨了，违规曝光没降 |
| **举报绝对数**| 减少曝光 / 限制分发 | 举报少了，用户也少了 |
| **举报率**| 无法靠缩量改善（分子分母等比下降） |  **相对指标天然抗这一类博弈**|
| **误伤率**| 放宽判定（把"可能违规"判成安全） | 误伤降了，底线漏放 |
| **漏放率**| 收紧判定 | 漏放降了，误伤爆炸 |
| **单条审核成本**| 降采样帧数 / 降判定频次 | 成本降了，召回崩了 |
| **人审量下降比例**| 把复杂 case 推给机器硬判 | 人审省了，申诉率上升 |

**所以本篇的核心命题是**：

> **不是"怎么选一个好看的指标"，而是"怎么设计一组不能被单方向博弈的指标"。**
> 单指标必然被博弈；换成**指标三元组**（效果 + 成本 + 规模），三者同时改善才算真改善。

**指标的三重身份**（决定了它必须由独立方管理）：
1. **度量工具**—— 描述现状（数据团队的职责）
2. **行为契约**—— 规定用力方向（业务方的职责）
3. **对外承诺**—— 向监管/公众交代（公共事务的职责）

⚠️ **这三重身份必须分离**。让 Policy 既定义规则、又评估水位（M1 §3.2 已指出），等价于让被考核者设计考核标准，是治理体系最典型的制度性缺陷。

## 一、四层指标架构

```
┌───────────────────────────────────────────────────────────┐
│ L1 合规层（对监管交代）                                    │
│   漏放率 · 阻断率 · 处置时延 · 专项达标率                   │
│   特征：绝对导向，不可谈判                                  │
├───────────────────────────────────────────────────────────┤
│ L2 生态层（对业务交代）                                    │
│   VVR · 低质 VV 占比 · 举报率 · 渗透率 · 负反馈率           │
│   特征：相对导向，看趋势与结构                              │
├───────────────────────────────────────────────────────────┤
│ L3 成本层（内部效率）                                      │
│   误伤率 · 申诉率与申诉成功率 · 人审量 · 单件成本 · SLA      │
│   特征：约束导向，决定自动化天花板                          │
├───────────────────────────────────────────────────────────┤
│ L4 过程层（诊断用，不可外传为结论）                         │
│   双审一致率 · 质检灰度率 · 机审召回 · 分流比 · 未覆盖样本    │
│   特征：解释"为什么变了"，不用于对外汇报                    │
└───────────────────────────────────────────────────────────┘
```

**两处必须建立的读法**：

**① 层的用途不同，不能混用。**用 L4 过程指标对外汇报会出现"双审一致率提升 5pt"这种内部人听得懂、外部人无法验证的表述；而用 L1 合规指标做内部诊断又太粗（一个漏放率涨了，可能是规则、模型、审核任一环节的问题）。

**② 滞后指标与先行指标要配对。**

| | 滞后指标（结果） | 先行指标（过程） |
|---|---|---|
| 例子 | VVR、举报率、低质 VV 占比 | 未覆盖样本池、双审一致率、申诉成功率突升 |
| 特性 | 反映影响，但**改动后很久才动**| 变动早，但**本身不是结论**|
| 用途 | 验收 | **预警 + 归因**|

⚠️ 只建滞后指标的组织永远是"事后救火"：等了两个月发现 VVR 没降，再回头查原因。**先行指标的价值在于把反馈周期从月压到周。**

## 二、口径定义的五个要素（缺一不可）

以最常被滥用的「**低质 VV 占比**」为例：

| 要素 | 必须明确 | 不明确的后果 |
|---|---|---|
| **分子**| 哪些视频算低质？**按谁的定义**？用哪个标签体系版本？ | 松紧变化直接改变结论 |
| **分母**| 全部 VV？还是仅推荐流 VV？站内是否含站外？ | 站内 vs 站外口径可能差数倍 |
| **时间窗**| 当日？7 日？**是否含老内容回扫**？ | 回扫上线会让指标瞬间跳变 |
| **加权**| 是否分用户 / 分品类 / 分场景加权？ | 头部品类会主导总体结果 |
| **版本**| 口径何时变更？**变更后是否回刷历史**？ | 跨期比较直接失效 |

### 2.1 第五条最容易被跳过：口径变更必须回刷历史

**口径改了但历史不回刷 = 跨期比较作废**。常见事故：
- 口径收紧（分子变大）→ 指标"恶化"，被误判为治理退步
- 口径放宽 → 指标"改善"，被当成治理成果汇报
- 分母范围调整（如纳入站外流量）→ 前后两期不可比

**规范做法**：
1. 口径变更走**变更单**（谁提、谁批、生效时间、影响面）
2. 变更时**同步回刷基线期数据**，并保留**口径版本号**
3. 对外汇报时标注口径版本；跨版本比较必须显式说明

### 2.2 一个高价值的简化：分子难定义时，改用现成信号

**误伤率是治理里最难精确测量的指标**——因为你无法穷举"被误伤但没申诉"的样本。

**工程解**：用**申诉成功率**作为误伤率的**先行代理指标**。
- 申诉是**天然存在的信号**（不需要额外抽样预算）
- 申诉成功率高 → 误伤严重（**这个方向是可信的**）
- 但要注意：低申诉率**不能反推低误伤率**（用户可能不知道申诉入口，或申诉成本高）

**所以正确用法**：`申诉成功率` 做预警，`抽样复核误伤率` 做验收，两者配对使用。

## 三、指标字典（可直接复用）

> 标注：**【官方】**= 平台公开披露；**【论文】**= 论文给出；**【建议】**= 本系列推荐口径（含抗博弈设计）
> ⚠️ 表中 `n/m` 表示"策略/模型"与"审核"两侧都可用的口径差异。

### 3.1 生态层（L2）

| 指标 | 定义 | 分母选择 | 时间窗 | 博弈风险 | 抗博弈设计 |
|---|---|---|---|---|---|
| **VVR**（违规曝光率） | 违规内容获得的观看量 / 总观看量 | 总观看量（**非推荐流**） | 季度（YouTube 惯例） | 提高判定口径→VVR 涨；降曝光基数→VVR 涨 | 以**观看量**为分母，**抗"多发内容摊薄"**|
| **低质 VV 占比**| 低质内容观看量 / 总观看量 | 建议同时出"推荐流"与"全站"两个口径 | 周（趋势）/ 月（验收） | 分子定义松紧 | 分子定义必须**版本化 + 回刷**|
| **举报率**| 举报数 / **曝光数**| **曝光数（不是内容数）**| 日（趋势）/ 7 日 | 分子分母**等比下降**，无法靠缩量改善 |  相对指标，天然抗博弈 |
| **举报有效率**| 判定成立的举报 / 总举报 | 总举报数 | 7 日（需等判定） | 用户滥用举报 → 有效率降 | 配对看，防"唯举报论" |
| **负反馈率**| 不喜欢 / 不感兴趣 / 拉黑数 / 曝光 | 曝光数 | 日 | 弱 | 与举报率趋势对照 |

**国际可比锚点**：
- **YouTube VVR**：自 **2020Q4**起按季披露，**公开历史值长期在 0.1%~0.2% 量级**【官方】——**目前最值得借鉴的单一生态指标**
- **TikTok**：披露"自动化检出占比"（2026Q1：下架 **184,012,576 条**，其中 **178,014,154 条（96.7%）由自动化检出**、主动处置率 99.3%、94.4% 于 24 小时内下架）【官方】**⚠️ 分母口径未公开，只能看趋势，不可横向比较**
- **Meta**：用 **prevalence（渗透率）+ 主动发现率**，而非"删了多少条"【官方】

### 3.2 合规层（L1）

| 指标 | 定义 | 关键注意 |
|---|---|---|
| **漏放率**| 事后抽查发现的违规 / 抽查总量 | ⚠️ **抽查的抽样偏差未知**——抽查只能证明"漏放不超过 X"，不能证明"漏放等于 X" |
| **阻断率**| 被成功拦截的违规 / 全部违规 | 分母依赖对"全部违规"的估计，通常来自抽查 |
| **处置时延**| 违规内容发布 → 处置生效 | 快手直播：**分钟级 → 秒级**【官方】 |
| **专项达标率**| 针对监管专项的达标情况 | 需与监管口径对齐，**不要自定义**|

⚠️ **最重要的一条**：**抽查漏放率与 VVR 应配对使用**。前者可操作、可归因（能查到具体类目），后者不可直接操作但**更接近真实影响面**。只报一个都有系统性缺陷。

### 3.3 成本层（L3）

| 指标 | 定义 | 关键注意 |
|---|---|---|
| **误伤率**| （申诉成功 + 质检推翻 + 事后复核改判）/ 处置总量 | **必须与漏放率并列报告**，只报一个必然失衡 |
| **申诉率**| 申诉数 / 处置总量 | 窗口过短会低估（用户要时间反应） |
| **申诉成功率**| 申诉成功数 / 申诉总数 | **误伤率的先行代理指标**；也反映规则可解释性差 |
| **人审量**| 转人工的条数 / 占比 | 与人效合看，防止"人审量降了但质量也降了" |
| **单件审核成本**| 含算力 + 人力 + 纠纷成本 | 决定自动化天花板（M2 §6.1） |
| **SLA**| P50 / P99 判定延迟 | 直播场景是硬约束 |
| **创作者/商家侧成本**| 误伤导致的工单量、申诉成本、GMV 影响 | **常被完全忽略，却直接落在业务上**|

**成本侧的三个一手标杆**：
- **误伤与漏放并列**：UNIVID **漏放 −42.7%、误伤 −37.0%**【论文】
- **跨域误伤**：SIRF 作树模型裁决层**多找回 20% 误罚样本**、跨域**误罚 −70%**【论文】
- **专家工时**：Amazon 商品质检 **5.1 小时/属性 → 3 分钟（−99%）**【论文】

### 3.4 过程层（L4，诊断用）

| 指标 | 定义 | 正确用法 | ❌ 错误用法 |
|---|---|---|---|
| **双审一致率**| 二次独立审核结论一致数 / 重审总数 | **诊断"规则可判定性"**（M1 §3.4） | 当审核员绩效指标（会逼出"抄上一次结论"） |
| **质检灰度率**| 抽检覆盖比例 | **抽检覆盖不足时，一切质量指标都不可信**| 只报抽检结果不报覆盖率 |
| **机审召回（分类目）**| 机审命中 / 人审认定违规 | **低于 40% 应回查规则可判定性**| 当成模型效果指标去调模型 |
| **分流比**| 各层处理量占比 | 容量规划（M2 §7.3） | 隐藏成本指标 |
| **未覆盖样本池**| 归不进现有规则的样本数 | **规则该不该迭代的先行指标**（M1 §3.2） | 不建池子，靠感觉判断 |

## 四、时效指标：治理体系最稀缺的公开数字

**"新规上线到全量生效需要多久"**是工业界几乎不公开、但业务上最关键的指标。它必须被拆成三段，否则无法定位瓶颈：

| 段 | 名称 | 瓶颈通常在哪 |
|---|---|---|
| ① | **规则定稿 → 策略上线**（编译时延） | 规则可判定性差 / 研发排期 |
| ② | **策略上线 → 灰度生效**（推送时延） | 工程链路 / 配置下发 |
| ③ | **灰度 → 全量放量**（放量时延） | 风险审批 / 观测周期 |

**目前能找到的锚点（按快慢排序）**：

| 手段 | 生效时延 | 来源 |
|---|---|---|
| **人审纠错回流**（MD5 命中即改判） | **约 10 分钟**| 腾讯云文档【官方】 |
| **直播违规识别**| **分钟级 → 秒级**| 快手直播【官方】 |
| **判例库 in-context 新增**| 无需重训（10 万条判例库） | UNIVID【论文】 |
| **争议样本天级更新**| **数百条数据 / 天级**| KuaiMod RLUF【论文】 |
| **语义热插拔**（新类零样本） | 写一条描述即可 | 快手开集 Tagging【官方】 |
| **政策内化（CPT）**| 需重训（70M token CPT） | SIRF【论文】 |
| **商品全生命周期回扫**| **未公开**（仅知"需回扫"） | 淘宝技术复盘【官方】 |

⚠️ **最后一行是全表最关键的空白**。商品治理的规则变更会**反向阻塞已发布商品**，回扫时延直接决定商家的实际损失——而这个数字**公开材料里完全没有**。这既是引用时的坑，也是从业者的真实机会点。

## 五、指标可靠性与抗博弈设计

### 5.1 四类博弈模式与对策

| 博弈模式 | 机制 | 典型场景 | 对策 |
|---|---|---|---|
| **摊薄型**| 扩大分母（多发内容），使比率改善 | 违规条数 / 内容总数 | 分母改用**观看量**（VVR 的设计） |
| **缩量型**| 减小分子分母（降曝光），使绝对数改善 | 举报绝对数、负反馈绝对数 | **改用相对指标**（举报率） |
| **搬迁型**| 把问题从被考核口径移到口径外 | 考核 A 类目→问题涌向 B 类目 | **指标必须按风险类分解，看最差类目**|
| **篡改型**| 直接污染数据源 | 审核员为达标改判 | 质检独立 + 双审一致率监控 + 申诉通道 |

### 5.2 指标三元组（本篇最核心的设计原则）

> **效果指标 ↑ + 成本指标 ↑ + 规模指标 ↑，三者同时改善才算真改善。**
> 只动一个，通常是在搬移问题。

**以"低质治理上线"为例的三元组**：

| 类别 | 指标 | 只改善这一个意味着什么 |
|---|---|---|
| 效果 | 低质 VV 占比 ↓ | 可能把有效内容一起限掉了 |
| 成本 | 误伤率 ↓ / 申诉成功率 ↓ | 可能放过了边界内容 |
| 规模 | 自动处置量 ↑ / 覆盖率 ↑ | 可能只是把口径放宽了 |

**三元组的落地形式**：一张固定报表，**每次汇报必须三个都给出**，不允许只报一个。这个制度设计比任何指标定义都更能防止治理走偏。

### 5.3 指标可靠性的六项验收

设计一个新指标时逐项自检：

| # | 验收项 | 合格标准 |
|---|---|---|
| 1 | **分子可归因**| 指标恶化时能定位到具体风险类/场景（否则无法行动） |
| 2 | **分母不可操纵**| 分母不由被考核方控制（内容数、曝光数由分发决定，相对安全） |
| 3 | **口径可版本化**| 变更能留档 + 可回刷历史 |
| 4 | **方向不可逆**| 指标改善**不可能**来自"少做事"（否则就是缩量型博弈） |
| 5 | **有先行指标配对**| 至少有 1 个过程指标能在结果指标变动前预警 |
| 6 | **有成本侧配对**| 效果指标必须有对应的成本指标（这是三元组的制度要求） |

⚠️ **第 4 项是最锋利的一条**：任何"少做事就能改善"的指标，最终一定会被发现并被利用。

## 六、实验设计与归因

### 6.1 治理实验的两个特殊困难

| 困难 | 原因 | 解法 |
|---|---|---|
| **不能随机分流**| 内容一旦违规就不该"随机放给一半用户" | **影子模式**（只判定不处置）+ 灰度放量 |
| **大盘波动干扰归因**| 生态指标受内容供给、季节、热点事件影响 | **双重差分（DID）**：处理组 vs 对照组的前后变化之差 |

### 6.2 分阶段评估（与 M2 §5.1 的五步上线严格对应）

| 阶段 | 评估什么 | 关键指标 |
|---|---|---|
| **标准/策略上线前**| 抽样预判 | 分层 gold set 的 **R@P**、误伤预估 |
| **影子模式**| **真实召回与漏放**（离线测不出） | 与线上策略的差异样本 |
| **灰度期**| 生态影响与成本 | 举报率、负反馈率、申诉率、SLA、分流比 |
| **全量后**| 稳态与副作用 | VVR、低质 VV 占比、**最差类目表现**|

⚠️ **Gap 提示**：**离线指标与线上生态指标之间的鸿沟是全链路最大的 gap**。离线 R@P 提升不等于举报率下降——中间隔着分流比、曝光结构、用户构成。**必须用影子模式 + 灰度来桥接，靠离线调参过不去。**（M2 §5.1 已指出，本篇给出指标侧的应对：影子阶段就要固定"差异样本池"，把鸿沟量化出来。）

### 6.3 归因框架（指标变了，先问是谁的问题）

| 观察 | 可能原因 | 先查哪里 |
|---|---|---|
| 某类目漏放上升，规则未变 | 数据漂移 / 对抗新变体 | 输入分布 PSI、对抗样本召回 |
| 全类目误伤上升，规则未变 | 阈值失配 / 置信度校准漂移 | 阈值重标、ECE/Brier |
| 举报率下降但申诉率上升 | 判定变松 | 误伤率、申诉成功率 |
| 低质 VV 占比突变 | **回扫上线**| 口径是否含回扫（§2 要素三） |
| 生态指标跨期不可比 | **口径变了**| 口径版本号与回刷记录 |
| 漏放与误伤同时恶化 | **规则不可判定**（M2 §9 核心结论） | 回 M1 改规则，不要在指标层调参 |

**最后两行是归因框架的价值所在**：它们把"看起来像模型问题/指标问题"的现象，准确地回推到了口径管理（M4）与规则定义（M1）。

## 七、指标治理的三方契约

指标不是某一方的资产。建议明确三方职责：

| 角色 | 职责 | 不负责 |
|---|---|---|
| **指标 owner（业务/Policy）**| 提出度量需求、解释业务含义、**承担行为契约后果**| 不自己计算、不自己评估水位 |
| **数据团队**| 口径实现、回刷、口径版本管理、**抽样方法设计**| 不决定指标方向（避免"数据迎合业务"） |
| **第三方/独立抽检**| **独立评估低质水位**| 不参与规则制定（M1 §3.2 的核心要求） |

### 7.1 口径变更流程（建议固化为制度）

1. **提出**：说明变更原因与预期影响面
2. **评估**：数据团队评估影响量级与是否需要回刷
3. **批准**：owner 批准，标注生效时间
4. **回刷**：同步回刷基线期，保留旧版本
5. **公告**：跨期比较时显式标注口径版本

⚠️ **没有这个流程的组织，一定会出现"口径随汇报需要灵活调整"**——而且通常不是恶意，是逐次妥协的结果。

## 八、常见反模式（自查表）

| 反模式 | 表现 | 根因 | 修法 |
|---|---|---|---|
| **单指标 KPI**| 只考核举报率或只考核漏放率 | 未做三元组 | 效果+成本+规模同时报 |
| **只报漏放不报误伤**| 误伤率长期不可见 | 考核缺成本侧 | 两个指标并列报告 |
| **口径不版本化**| 跨期比较直接失效 | 无口径字典 | 五要素 + 变更流程 + 回刷 |
| **用外部披露数字做内部 KPI**| 拿 Amazon 99.9%、TikTok 96.7% 当目标 | 自述口径分母未公开 | 对外引用官方口径，对内自建口径 |
| **回扫未标注**| 指标突然跳变无法解释 | 分子含回扫但未注明 | 口径注明是否含回扫 |
| **双审一致率当绩效**| 审核员互相抄结论 | 指标用途错配 | 只用于诊断规则可判定性 |
| **只报抽检结果不报覆盖率**| 质量数据不可信 | 缺质检灰度率 | 二者必须同时报 |
| **滞后指标独大**| 永远事后救火 | 无先行指标 | 建"未覆盖样本池""申诉成功率"监控 |
| **分子不可归因**| 指标恶化但不知道做什么 | 未按风险类分解 | 所有生态指标必须分解到类目 |
| **"少做事就能改善"的指标**| 被系统性利用 | 违反可靠性验收第 4 项 | 换相对指标或加规模指标约束 |
