## 〇、先纠正一个前提误区

**❌ 误区**：审核是"处理量"的工厂——人越多、判得越快，治理就越好。

**实情**：审核在全链路里有**两个身份**，而第二个身份才是它不可替代的原因：

| 身份 | 作用 | 可否被替代 |
|---|---|---|
| **① 产能**：批量判定内容 | 消耗人力出结论 |  **正在被大规模替代**（快手磁力引擎："部分一线审核员实际上已经被大模型替换掉了"） |
| **② 度量**：**全链路唯一能给出"真值"的地方**| 提供人审真值，用来校准机审、评估规则、验收策略 | ❌ **不可替代**——机器无法自己证明自己对 |

**这个判断有几个直接推论**：

1. **人审的价值锚点从"产能"转向"度量"**。快手把"智能标注自动化率"目标定到 **≥70%**、并说"部分一线审核员已被替代"，同时把运营岗升级为"**模型教练**"（M1 §7.3）——被替代的是产能身份，被强化的是度量身份
2. **人审量下降不等于治理进步**。人审量下降若伴随"申诉率上升、双审一致率下降"，说明度量能力也一起被削掉了，后果会在 3~6 个月后以"模型悄悄失准"的形式爆发
3. **派单与抽检必须分开设计**。"判多少"是产能问题（可以用成本模型优化），"依据什么判、判完怎么验"是度量问题（不能省）

**审核还有一个不能只用效率谈的成本**（KuaiMod 论文原文把它列为**人工审核的三大弊端之一**）：**审核员心理负担**。长期接触底线违规内容会造成真实伤害——这一点在任何效率模型里都不该被忽略。

## 一、主流程：三类审核的分工

> 业界常见审核链路在主流程上分为三类：**安全审核、质量审核、高热审核**。三类的**发布时机**与**派单逻辑**完全不同。

| 类型 | 审什么 | 发布时机 | 逻辑 | 优先级 |
|---|---|---|---|---|
| **安全审核**| 高风险红线问题 | **先审后发**| 审核完成前内容**不可推荐**| 最高，一票否决 |
| **质量审核**| 低质问题 | **先发召回**| 通常先发布召回；**进审是否影响推荐状态取决于多重因素**| 中，可排序可延迟 |
| **高热审核**| 头部内容画风 | 发布后复审 | 对头部内容做最后一道人工把关 | 高（因影响面大） |

### 1.1 为什么质量审核「先发召回」、安全审核「先审后发」

这不是拍脑袋，而是**误判代价的不对称**决定的：

| | 先审后发（安全） | 先发召回（质量） |
|---|---|---|
| 漏放一次（FN） | 违规内容进入分发，**不可逆**，可能触发监管风险 | 低质内容被消费一小段 |
| 误判一次（FP） | 创作者/商家**发不出去**，体验伤害大 | 内容被移出推荐，可恢复 |
| 主导风险 | **漏放不可逆**→ 必须前置 | 误判可逆 → 允许后置 |
| 代价 | 发布延迟（创作者体感差） | 需时效保障（否则召回太晚没意义） |

**所以"先发召回"能不能成立，取决于一个硬条件：时效**。

- 快手直播给出了参照：**"部分低俗违规内容识别时效从分钟级降至秒级"**；日均关闭 **>1500 个**低俗违规直播间
- 极限情况是**直播**——直播流无法"先审后发"、也几乎无法"召回"（内容已经播出去了），所以直播治理**本质上只有"秒级干预"一条路**，这决定直播的审核链路设计与点播完全不同

⚠️ **质量审核进审是否影响推荐状态，取决于四个因素**（工作笔记给出，建议加为第五项）：

1. 审核处理时效
2. 召回优先级
3. 业务本身诉求
4. **内容所处的分发阶段**（冷启期 / 成长期 / 成熟期，见 M2 §2.1 审核结果作负向信号）
5. **（建议新增）创作者的历史信用与服务考核**——同等低质下，惯犯与初犯的处置应不同

### 1.2 高热审核：为什么必须单独做一次

**工作笔记给出的原理**：从各平台消费结构看，**头部聚集效应异常强烈——10% 的内容能撬动 90% 的流量**，因此保证头部内容的画风健康非常重要。

> ⚠️ "10%/90%" 是行业通行的量级描述，**本次调研未取得一手出处**，引用时建议写成"头部内容的流量集中度极高"而不是精确引用该比例。

**技术侧的一手印证**：KuaiMod 的在线精修专门引入了一个队列——**High-Engagement Videos（当日最热视频）**，理由写得很明确：*"这些视频有大量受众，意味着其中的任何违规都会对平台生态系统造成更大风险"*，且*"热门内容的快速变化直接反映平台趋势与用户偏好"*（[arXiv:2504.14904](https://arxiv.org/abs/2504.14904) §4.4.2）。

**高热审核的三个特殊价值**：

1. **风险杠杆最高**：一条头部内容的违规，影响面 ≈ 一条长尾内容的数万倍
2. **趋势信号**：热门内容直接反映平台当下的风格迁移，是**规则的先行指标**（M1 §四的迭代触发器）
3. **对推荐模型的影响**：审核结果作为负向信号时，头部内容的判定会影响正负样本量级（见 §四）

### 1.3 送审顺序与召回优先级

```
新内容入库
   │
   ├─→ L0 规则层（词典/正则/图谱）  ── 确定黑白，成本≈0
   │
   ├─→ 安全审核（先审后发）           ── 一票否决；未过审不可推荐
   │
   ├─→ 质量审核（先发召回）           ── 按召回优先级派单
   │
   └─→ 发布 ──→ 高热审核（发布后复审） ── 头部内容最后把关
                    │
                    └─→ 质检抽检（贯穿全流程）→ 反推前序环节问题
```

**派单优先级的三条常用依据**：召回优先级（风险等级）＞ **预期影响面**（预估曝光/作者粉丝量）＞ **时效诉求**（越靠近热点越优先）。

## 二、召回总览：谁决定"哪些内容该进审核"

> **召回的定位**：把**全量内容**筛成**待审队列**。它是审核链路的入口，也是整个治理体系里**唯一直接决定"人力与算力花在哪里"的环节**。
>
> ⚠️ **边界说明**：本篇讲**平台侧**的召回（机审扫描、人审补位、巡检、回流信号）。**举报产品的策略独立成篇（见 M9）**，申诉见 M5。三者分工见本节 §2.9。

### 2.1 召回是审核的入口，也是成本的闸门

**召回天然是一个"资源分配"问题，而不是一个"技术"问题**：

```
全量内容（100%）
   │  召回：按信号筛出候选
   ↓
待审队列（x%）  ← x 由「人力上限 ÷ 单条审核成本」反推
   │  审核：人审 / 机审
   ↓
处置（更小的比例）
```

⚠️ **召回率与检出率是两个概念，不能混**：

- **召回率**：该审的内容里，有多少被送进了队列
- **有效送审率**：送进队列的内容里，有多少最后被确认有问题

**召回的失败有两种，成本完全不同**：

| 失败类型 | 后果 | 谁来承担 |
|---|---|---|
| **漏召**（该审没送审） | 违规内容在线传播 | 用户 / 监管 |
| **误召**（不该审送了审） | 浪费人力、内容被停推（创作者损失） | 审核团队 / 创作者 |

⚠️ 工作笔记中"**被举报内容待审期间通常为不可推荐状态**"这条，说明**误召的成本不只是人力，还包括被误召内容的曝光损失**（详见 M9）。

### 2.2 召回的七个来源

| 来源 | 触发机制 | 覆盖什么 | 成本 |
|---|---|---|---|
| **① 机审全量扫描**| 模型对全量内容打分 | **已知问题域**（有规则的部分） | 算力 |
| **② 人审补位**| 抽检、专家队列 | 机审盲区、边界 case | 人力 |
| **③ 巡检**| 主动巡查、监控报警 | **未知变体**（M0 §四） | 人力 |
| **④ 举报**| 用户负反馈 | 用户感知到的问题（**独立成篇 M9**） | 人力 |
| **⑤ 申诉回流**| 用户翻案 | **判罚错误与规则缺陷**（M5） | 人力 |
| **⑥ 消费/行为信号**| 后验指标异动（完播、负反馈、异常增长） | 表现异常但未命中规则的内容 | 低 |
| **⑦ 主动学习**| 模型不确定样本回流 | 模型能力边界 | 低 |

⚠️ **一个关键判断**：

> **来源 ① 只能覆盖"已知问题"，来源 ③④⑤ 才是"未知问题"的入口。**
> 这与 M0 §二 的"感知半径"是同一件事——**只靠机审全量扫描的召回体系，会在所有新风险上都慢半拍**。

**来源 ⑥ 的成本最低、最被低估**：它是**唯一不需要额外人力或算力的召回通道**，且天然按"影响面"排序（消费异动本身就是影响力信号）。

### 2.3 风险环节划分：串行 vs 并行（接 M8）

**这是召回设计里最重要的一条分域差异**：

| 体裁 | 风险环节 | 划分依据 | 含义 |
|---|---|---|---|
| **图文 / 短视频**| **串行**| **基于消费情况划分**| 内容先跑起来，看消费表现（VV、互动）再决定进不进审——这是"先发召回"的召回侧实现 |
| **直播**| **并行**| **基本不依赖消费情况划分**| 内容在播时消费正在发生，**无法等后验信号**，只能靠实时流与行为信号触发 |

⚠️ **实操含义**：**图文策略可以"用消费数据当召回信号"（高热内容先审），直播策略不能**（M8 §3.1）。

### 2.4 召回的三级分层（接本节 §一）

| 层级 | 召回对象 | 时机 | 逻辑 |
|---|---|---|---|
| **高危前置**| 底线类、确定高风险 | **先审后发**| 未过审不可推荐 |
| **低危后置**| 质量 / 低质类 | **先发召回**| 按优先级派单 |
| **高热复审**| 头部内容 | 发布后 | 头部聚集效应强，需最后把关 |

### 2.5 召回的成本约束：人力上限是第一约束

> **工作笔记（举报场景，但适用于全部召回）**：在当前的经济环境下，互联网增速放缓，业务成本是无法回避话题，因此**实际的业务落地必须要考虑人力成本上限内可承担的最大进审量**。

**由此得到召回策略的目标函数**：

```
在「日进审量 ≤ 人力上限」的约束下
   最大化 [ 召回覆盖率 × 有效送审率 ]
```

⚠️ **这个函数解释了为什么不同的召回来源要用不同的阈值策略**：

- **机审扫描**覆盖全量、成本低 → 阈值可偏**召回优先**（多送一些无妨）
- **人审 / 巡检**覆盖窄、成本高 → 阈值必须偏**精度优先**（每条工单都要值得审）

这与本篇 §四"机审要精度、人审要命中量"的结论**并不矛盾**：那里的"机审要精度"指的是**机审作为终局判罚者**时要精度；**机审作为召回器**时反而应该召回优先。

### 2.6 召回与下游的接口

| 接口方向 | 交出去什么 | 下游需要什么 |
|---|---|---|
| 召回 → 审核 | 待审队列 | **优先级 + 召回原因 + 疑似风险类型**（只给排序不够） |
| 审核 → 召回 | 判定结果 | 反馈"哪类召回来源的命中率低"，用于调整阈值 |
| 召回 → M1 | 未覆盖样本 | 规则缺口信号 |
| 召回 → M2 | 阈值反馈 | 分流比与成本约束 |

⚠️ **"召回原因"是常被省略但极有价值的信息**：审核员知道"这条是因为举报率高被召回的"还是"因为模型不确定被召回的"，**判罚效率与一致性都会更高**（对应本篇 §四"人审工单的值得审"）。

### 2.7 召回的校验三维度

| 维度 | 核心指标 | 过程指标 |
|---|---|---|
| **覆盖**| **分类目召回率**、未覆盖样本池 | 各来源的贡献占比 |
| **有效**| **有效送审率**（命中 ÷ 进审） | 各来源的命中率对比 |
| **成本**| 进审量 ÷ 人力上限、单条进审成本 | 误召导致的停推时长（创作者侧损失） |

### 2.8 组织维度的关键区分：平台侧信号 vs 用户侧信号

**这一条是本篇最容易被忽略、但对组织协作最重要的一点**：

| | **平台侧召回信号**| **用户侧召回信号**|
|---|---|---|
| 谁会用到 | 算法工程师、机审策略、审核运营、质检 | **审核产品团队**|
| 典型信号 | 机审打分、模型不确定度、消费 / 行为后验、巡检规则 | 举报、申诉 |
| 触发者 | 平台 | **用户**|
| 优化目标 | 召回率 / 准确率 | **审核产品体验、用户信任、信号质量**|
| 独立模块 | 本篇 M3（召回）+ M2（策略） | **M9（举报）+ M5（申诉）**|

⚠️ **为什么必须分开看**：

> **平台侧信号的输入是"内容"，用户侧信号的输入是"人"。**
> 前者只需要内容理解能力；后者还要处理**用户动机**（真实反感 / 恶意 / 试探 / 维权），并且**直接决定用户对平台的信任感**——举报入口的可用性、申诉结果的透传，都是产品问题，不是模型问题。

**所以这三套系统由不同团队负责是合理的**：召回偏算法与策略，举报与申诉偏产品与运营。**本系列因此把它们拆成三个独立模块。**

### 2.9 三个独立模块的分工（召回 / 举报 / 申诉）

| | **召回**| **举报**| **申诉**|
|---|---|---|---|
| 模块 | **本篇 M3**| **M9**| **M5**|
| 发起方 | 平台 | **用户（消费者）**| **用户（被处置方）**|
| 本质 | **筛选**| **发现**| **纠错**|
| 回答什么 | 哪些内容该进审核 | 哪些内容用户认为是问题 | 哪些处置用户认为判错了 |
| 成本结构 | 人力预算下的召回率最大化 | 无效举报稀释有效送审 | 复核成本 vs 挽损收益 |
| 主要接口 | → M2 策略、M1 规则缺口 | → M0 风险感知、M1 规则迭代 | → M1 规则迭代、M4 误伤口径 |

**一句话区分**：**召回是平台主动找要审的，举报是用户告诉你该审的，申诉是用户告诉你不该罚的。**
## 三、送审策略：机审要精度、人审要命中量（笔记核心，附推导）

> **工作笔记原文**：

> - 送审策略追求两个目标：**「更多」和「更准」**

> - **用于机审**：准确率 > 召回率

> - **用于人审**：命中量 > 准确率

这是整份笔记里最"反教科书"、也最容易被追问的一条。**把它讲透的方法是把两种审核模式在链路中的位置说清楚**：

| | 机审策略 | 人审策略 |
|---|---|---|
| **在链路中的位置**| 通常是**最终判罚者**（直接判罚，无下游复核） | **劳动力瓶颈环节**，下游只有成本，没有更多校验 |
| **误判的代价**| **准确率低 = 误伤直接生效**，不可逆（申诉成本高） | 准确率低只是**加工了无效工单**，但因为下游就是执行，所以"命中量"直接等于产出 |
| **真正的约束**| **处置正确性**（申诉率、创作者体验） | **产能有限**（人力是最贵的资源） |
| **因此优先指标**| **准确率 > 召回率**| **命中量 > 准确率**|

### 4.1 这条原则有一个必须加上的限定（否则会误导）

**"机审要精度"只对"机审是最终判罚者"的环节成立。**分级看：

| 机审的角色 | 优先 | 例子 |
|---|---|---|
| **直接判罚（终局）**| **精度优先**| 机审判定即删/即限 |
| **仅做初筛（下游有人审复核）**| **召回优先**| 机审捞候选送人审 |
| **风险分级路由**（送人审 or 直接处理） | **看下游有没有兜底**| 无兜底→精度；有兜底→召回 |

⚠️ **这和本篇 §二的分支链路是同一件事**：机审到底该精度优先还是召回优先，**取决于下游有没有兜底**。所以"用于机审的策略更关注准确率"这句话的完整版是：

> **机审策略的精度/召回优先，由"机审是不是终局判罚"决定；是终局判罚就要精度（因为误伤不可逆），是初筛就可以放宽精度换召回（因为下游有人审兜底）。**

### 4.2 但还有第二层：**按风险类再分一次**

这也和 M2 §4.1"阈值必须按风险类分别标定"完全一致：

| 风险类 | 漏放代价 | 误伤代价 | 优先 |
|---|---|---|---|
| **红线类**（涉恐、涉未成年、违禁品） | **极高，不可逆**（监管风险） | 高，但可控 | **召回优先**|
| **低质类**（搬运、标题党） | 低（体验损失，可恢复） | 中（创作者体验） | **精度优先**|

→ **最终表述**：

> 机审策略的指标排序不是一个固定答案：**先看机审是不是终局判罚（决定精度还是召回），再按风险类分开定（红线类召回优先、低质类精度优先）**。而"人审更关注命中量"这一条是稳定的——因为人审的约束始终是产能。

### 4.3 为什么人审的约束是产能：几个量级感

| 数据 | 数值 | 来源 |
|---|---|---|
| 快手 KuaiMod 全量机审能力 | **48×RTX4090 / QPS 6.81 / 60 万条/日**| KuaiMod 论文 |
| 同上，摊到单卡 | 约 **7 秒/条**（视频多帧 VLM） | 论文推算 |
| 淘天生鲜商品单图审核 | 双卡 L20 约 **10 QPS**（约 0.2 秒/条） | 官方分享 |
| 阿里云大模型审核容量红线 | 视频 **10 路并发**、直播 **5 路**| 阿里云文档 |
| TikTok 自动化检出 | 2026Q1 下架 1.84 亿条，**96.7% 自动检出**| TikTok 报告【自述】 |
| 快手商业化前置小模型拦截 | **>80%**常规案例 | 王东旭 AICon |

**读法**：机审一天的产出（60 万条）与 TikTok 一季度下架量（1.84 亿条）之间的量级关系，说明**人审只能覆盖极小的比例**——所以人审的每一条工单都必须"值得审"。**"命中量"本质上是在衡量"人力的浪费率"**。

### 4.4 一个被这条原则带出来的配套问题：人审工单的"值得审"怎么保证

| 手段 | 做法 | 效果 |
|---|---|---|
| **提升送审精度**| 只把高置信违规送人审 | 减少无效工单（但会漏掉边界） |
| **物料指纹去重**| 相同/近似物料不重复审 | 腾讯纠错名单：**MD5 命中即按纠错后标签输出，约 10 分钟生效**|
| **难例优先**| 置信度灰区、对抗样本、高热内容优先 | 人力投在真正的难点上 |
| **人审只做"机器做不了的"**| 主观尺度、跨模态矛盾、需要外部知识的判断 | 发挥度量身份（§〇） |

## 四、质检策略：发现"问题"，而不只是发现"执行问题"

> **工作笔记原文**：

> - 质检策略的核心目标在于**发现问题，但不局限于发现执行问题**

> - **执行问题**→ **badcase 检出率**是关注核心

> - **同时也可以利用其他指标发现其他潜在问题**，比如**灰度率可以反推前序环节问题**

### 5.1 执行问题 vs 非执行问题

| 类型 | 定义 | 归因 | 修法 |
|---|---|---|---|
| **执行问题**| 审核员判错了（认知偏差、疲劳、理解错误） | 审核侧 | 培训、案例对齐、复训 |
| **非执行问题**| 审核员**按规则判对了**，但结果仍然不对 | **规则侧或模型侧**| 回 M1 改规则 / 回 M2 改模型 |

⚠️ **这个区分是本模块最重要的一个判断**：

> **"审核员按规则判对了，但用户仍然不满"——这不是执行问题，是规则问题。**

> 它的正确动作是回 M1 迭代规则，而不是培训审核员。

**这正是 M1 §3.4「认知对齐测试」要捕捉的东西**：如果 3~5 名审核员对同一条规则的理解不一致，那不是"培训没做好"，是**规则表述有歧义**。质检的价值就在于**把这类信号从"人的问题"里剥出来**。

**技术侧的一手印证**（KuaiMod 的一个精巧设计）：

> 对"模型判对、但用户仍感不适"的样本，让大模型在推理中**列举可能引起不适的方面，并解释为何不违规**——用于教模型区分 **个体敏感 vs 社会共识**。

→ **同理，质检也应沉淀两类资产**：

- **"为什么违规"的判例**→ 防漏放
- **"为什么不违规"的判例**→ 防误伤（**多数团队只做前者**）

### 5.2 灰度率：一个被低估的诊断指标

> **常见考点：如何利用灰度率反推前序环节问题？**

**灰度率 = 抽检覆盖比例**。笔记给的关键洞察是：它不只是"质量数据的可信度前提"，还可以**反推前序环节的问题**。

**反推逻辑（本篇补充的四种诊断）**：

| 观察 | 反推 | 指向 | 动作 |
|---|---|---|---|
| 灰度率偏低 | 质量数据本身不可信 | 质检体系 | 先提覆盖率，再谈质量结论 |
| 灰度率够，但某类目**执行问题检出率极低**| 要么规则太清晰不必抽，要么该类目送审量本身极少 | 送审策略 | 回查该类目召回是否缺失 |
| 灰度率够，但某类目**长期查不出问题且送审量很大**| 送审策略过宽，**人审资源被浪费**| 送审策略 | 收窄该类目阈值 |
| 灰度抽检发现**规则违规但机审漏了**| 机审召回不足 | 模型 | 补难例、查可判定性（M1 §3.4 机审召回体检：低于 40% 回查规则） |

**灰度率的第二种用法（笔记提到但未展开）**：**用灰度率反推审核员的人效与疲劳**——相同类目下，灰度率高的时段双审一致率若下降，提示是人（疲劳）而不是规则。

### 5.3 质检的完整产出

| 产出 | 内容 | 下游 |
|---|---|---|
| **执行质量报告**| badcase 检出率、分类目错误分布 | 培训体系、复训 |
| **规则反馈单**| "按规则判对但结果不对"的案例 | **M1 Policy**（迭代触发器） |
| **模型反馈单**| "规则清楚但机审漏"的案例 | **M2 Strategy**（补难例/查可判定性） |
| **标准工时与人效数据**| 分类目单条耗时 | M2 成本模型、派单优化 |
| **负向判例库**| "为什么不违规"的案例 | 全链路防误伤 |

## 五、推荐场景：审核结果如何影响推荐

> **工作笔记原文**：

> - 直接作用：被审核策略召回的内容，其**审核结果直接干预推荐状态**

> - 间接影响：在一些平台的推荐模型中，**审核结果可以作为负向信号**用于冷启、排序、策略等环节，因此被召回的人审内容在一定程度上**影响着正负样本的量级**；此外策略召回的精准度，**尤其应用在机审环节的策略，与创作者体验有直接关系**

### 6.1 直接作用：三条干预路径

| 路径 | 机制 | 一手案例 |
|---|---|---|
| **不推荐**| 违规内容移出推荐池 | KuaiMod："videos identified as violative are **directly removed from promotion**" |
| **个性化推荐**| 判定结果作推荐特征，不同用户不同策略 | KuaiMod 嵌入推荐特征 → **DAU +0.028%、人均 AUT +0.033%、总 AUT +0.063%**|
| **冷启干预**| 审核结果作为冷启阶段的负向信号 | 工作笔记（间接影响） |

⚠️ **"个性化"的边界必须写清**（KuaiMod 原文）：**只有部分违规类型可以保留用于个性化推荐；明确违法或造成严重危害的视频被严格过滤。**这与 M1 §1.4"法律底线不能个性化、生态水位可以个性化"完全一致。

### 6.2 间接影响：为什么"正负样本量级"是审核指标

这是最容易被忽略的一条因果链：

```
送审/召回策略 → 被召回的内容进入人审 → 审核结果 → 推荐模型的负向信号
                                    ↓
                        正负样本量级变化 → 排序/冷启/策略效果
```

**它带来的一个管理含义**：

> **审核结果不只是"处置决策"，还是"训练数据"。**所以送审策略一旦变化（阈值放宽/收窄），**会同时改变推荐模型的训练数据分布**——这是一个跨团队的隐含影响，M2 在设计阈值时必须和推荐团队对齐。

### 6.3 与创作者体验的关系（笔记原文最后一句，值得单独强调）

> **策略召回的精准度，尤其应用在机审环节的策略，与创作者体验有直接关系。**

**因果链**：机审精度低 → 误伤创作者内容 → 创作者感知"平台乱判" → 供给意愿下降（B 端指标，M1 §3.2 列为过程关注指标：**B 端创作者体验**）。

**这解释了为什么"机审要精度"是一个体验约束而不是效率约束**：机审误伤的承受方是**内容的生产者**，而内容生产者是平台的供给来源。损失一条视频是小事，损失一个持续创作者是系统性的。

## 六、审核质量的三维度校验（与前两篇平行）

| 维度 | 核心指标 | 过程指标 | 说明 |
|---|---|---|---|
| **认知对齐**| **双审一致率**| 认知对齐测试通过率 | 规则可判定性的核心诊断（M1 §3.4） |
| **效能平衡**| **人效（分类目单条耗时）、分类目 badcase 检出率**| **质检灰度率**、送审命中量 | 效率与质量应**同时向好**；只动一个必是搬移问题 |
| **度量有效性**| 人审真值对机审的可校准性（ECE/Brier） | 反馈单产出量（规则/模型） | 人审是否真的在提供"真值"而非"重复机审" |

**⚠️ 第三维度是新增的，也是本模块存在的理由**：如果人审只是"把机审的结论又抄了一遍"，那它既不提供产能也不提供度量，就应该被自动化替代。**检验方法**：随机抽取人审推翻机审的样本，看推翻理由中有多少能归成"规则表述问题"或"模型特征不足"——**如果归不进去，说明人审在提供真值；如果全都能归成"机审阈值太松"，说明这个环节可以取消。**

## 七、常见反模式（自查表）

| 反模式 | 表现 | 根因 | 修法 |
|---|---|---|---|
| **审核只当产能**| 只考核量、速度、成本 | 忽略度量身份 | 加双审一致率、反馈单产出量 |
| **把非执行问题当执行问题**| 反复培训审核员但误伤不降 | 未区分问题类型 | 建"按规则判对但结果不对"的反馈单 |
| **双审一致率当绩效**| 审核员互相抄结论 | 指标用途错配（M4 §3.4） | 只用于诊断规则可判定性 |
| **只报抽检结果不报覆盖率**| 质量数据不可信 | 缺灰度率 | 二者必须同时报 |
| **人审量下降当成绩**| 申诉率悄悄上升 | 度量能力被削 | 人审量下降必须与申诉率、一致率同看 |
| **质量审核进审无预案**| 审核延迟导致内容"含着违规被推" | 未定义进审对推荐状态的影响 | 明确四因素决策（本篇 §1.1） |
| **高热审核缺位**| 头部内容违规才发现 | 无头部复审环节 | 建 High-Engagement 队列（KuaiMod 做法） |
| **直播照搬点播链路**| 想"先审后发"直播 | 未识别形态差异 | 直播只有秒级干预路径 |
| **只沉淀"为什么违规"**| 误伤反复出现 | 缺负向判例 | 同等沉淀"为什么不违规" |
| **发货/商品不回扫**| 规则变了存量不动 | 缺回扫机制 | 全生命周期回扫（M1 §五、M2 §5.2） |
